---

## 0. 一句话职责

**回答「现在该不该补货、补多少件」，并且只回答这个。**

不回答：该不该涨价、该不该清仓、这单赚多少、这个品要不要继续做。

---

## 1. 为什么要有这个 Agent

平台把「可售库存」和「实仓库存」两个数放在一起，但它们不是一回事：

| 口径 id | 含义 | 实测值（400370，2026-11） |
|---|---|---|
| `inventory.sellable` | 平台可售额度 | 213,682 件 |
| `inventory.actual` | 实仓在库 | 1,264 件 |

差了两个数量级。**拿 `inventory.sellable` 算补货，会得出「库存够卖几十年」的结论，然后整店断货。**

这就是本 Agent 存在的理由：**把补货判断锁在物理库存上，并且让口径错误无法静默通过。**

---

## 2. 输入：只读，且只认这 5 个口径

来自 `config/metrics-schema.json`（33 个口径中的 5 个，**不许自造字段名**）：

| 口径 id | 用途 | 单位 |
|---|---|---|
| `inventory.actual` | 物理在库，补货计算的**基数** | 件 |
| `inventory.occupied` | 已被订单占用、未出库 | 件 |
| `inventory.transit` | 已发往平台仓、未入库 | 件 |
| `sales.qty.total` | 含货通销量，算**件数**销速 | 件 |
| `sales.qty.direct` | 不含货通销量，用于对照 | 件 |

### 2.1 硬性禁止

| 禁止项 | 原因 |
|---|---|
| 用 `inventory.sellable` 算覆盖天数 | 平台可售额度 ≠ 物理库存（213,682 vs 1,264） |
| 混用 `sales.qty.total` 与 `sales.qty.direct` | 同店同期两个数不同，混用即口径污染 |
| 用 `conv.buyers` 算件数 | 那是**订单/买家**量纲，不是件数 |
| 输出任何金额（采购成本、毛利、ROI） | **`metrics-schema.json` 里没有任何成本/COGS 口径**，算钱就是编数 |
| 采集 15:00–17:00（北京）的日切数据 | 平台此时归零，写入即污染 |

> 最后一条尤其重要：C3（核准 COGS）还没做完，所以在 COGS 落地前，本 Agent **在结构上就不具备算钱的能力**。这不是"暂时不算"，是"声明里没有这个能力"。

## 3. 计算：一个公式，三个参数

```
物理可用 = inventory.actual − inventory.occupied + inventory.transit
日均销速 = Σ sales.qty.total(近 N 天) ÷ N        N ∈ {7, 14, 30}
覆盖天数 = 物理可用 ÷ 日均销速
建议补货件数 = 日均销速 × (补货周期 + 安全天数) − 物理可用
```

默认参数（改这里就是改行为，不藏在代码里）：

| 参数 | 默认 | 依据 |
|---|---|---|
| 销速窗口 N | 14 天 | 7 天噪声大，30 天对季节品迟钝 |
| 补货周期 | 25 天 | 采购 7 + 国内集货 3 + 头程 12 + 清关入仓 3 |
| 安全天数 | 10 天 | 覆盖头程波动 |
| 最少起补量 | 20 件/规格 | 低于此不建采购单，避免碎片单 |

### 3.1 五种结论（必须五选一，不许模糊）

| 结论 | 条件 | 动作 |
|---|---|---|
| `RESTOCK` | 覆盖天数 < 补货线 **且** 建议补货 ≥ 最少起补量 | 出采购建议，进 HUMAN_GATE |
| `WATCH` | 覆盖天数 < 补货线 **但** 建议补货 < 最少起补量；**或** 覆盖天数在 [补货线, 90] 区间 | 只标记，不出单 |
| `OVERSTOCK` | 覆盖天数 > 90 | 只标记，**不自动降价、不清仓** |
| `DEAD_STOCK` | 近 30 天 `sales.qty.total` = 0 **且** 累计销量 ≥ 50 | 标 P0 观察，**严禁按长尾处理** |
| `NO_HISTORY` | 历史天数 < 7 | 不出结论，交人判断 |

其中 `补货线 = 补货周期 + 安全天数 = 35 天`。三档必须**无缝覆盖**（0–35 / 35–90 / >90），不允许留空档——留空档就等于让实现自己发挥。

`DEAD_STOCK` 是这张表里最危险的一格：累计卖过 50 件以上但 30 天零销，最容易被当成"卖不动"清掉，实际往往是断货、断码或链接被降权。**这个判定只做标记，永远不产出清仓动作。**

### 3.2 判定顺序（必须按这个顺序短路，不许并行判断）

1. 日切窗口 → 命中即 `REFUSE`，**不进入任何计算**
2. 必需口径缺失 → `FAIL_CLOSED`，**不进入任何计算**
3. 历史天数 < 7 → `NO_HISTORY`，**先于数量结论**
4. 近 30 天零销且累计 ≥50 → `DEAD_STOCK`
5. 其余按覆盖天数落 `RESTOCK` / `WATCH` / `OVERSTOCK`

顺序不能换。反例：新品 5 天卖出 15 件、库存 300 件，若直接算覆盖天数 = 100 天，会被判成 `OVERSTOCK`（积压），而真相是"数据不够，什么都判断不了"。**同一个输入，顺序错了结论就反了。**

### 3.3 数量上限的处理方式

`建议补货件数` 超过单 SKU 上限 500 时，**不许截断成 500，也不许原样输出**，必须拆成多单（每单 ≤500）并要求逐单确认（`SPLIT_AND_REQUIRE_HUMAN`）。截断等于偷偷改需求；原样输出等于绕过上限。

## 5. 权限上限（硬约束）

| 维度 | 上限 | 超限行为 |
|---|---|---|
| 副作用等级 | **P0 + P1** | 任何 P2 以上直接拒 |
| 单 SKU 单次建议量 | ≤ 500 件 | 超过则拆单并要求人确认 |
| 单次采购单总件数 | ≤ 2,000 件 | 超过直接拒 |
| 单次覆盖 SKU 数 | ≤ 50 | 超过拆批，避免一次看不过来 |
| 输出金额 | **0** | 任何金额字段出现即整单 REJECTED |
| 写平台 | **禁止** | 采购单只能落本地草稿 + 等人点 |

`≤ 500 件/SKU` 与 `≤ 2,000 件/单` 不是拍脑袋：它们让"一次误判"最多损失 2,000 件的资金占用，而不是整店。

## 6. 失败模式与兜底

| 编号 | 失败 | 兜底 |
|---|---|---|
| PI-01 | 某个口径缺失 | **fail-closed**，整批不出结论，报 `CALIBER_MISSING` |
| PI-02 | 数据落在 15:00–17:00 日切窗口 | 拒绝计算，报 `DAY_CUT_WINDOW`，等下一窗口 |
| PI-03 | 日均销速为 0 但累计 ≥50 | 判 `DEAD_STOCK`，禁止输出补货建议 |
| PI-04 | 日均销速为 0 且累计 <50 | 判 `NO_HISTORY`，不出结论，交人判断（新品/冷启动） |
| PI-05 | 建议量超过单 SKU 500 件 | 拆为多单，每单 ≤500，并要求逐单确认 |
| PI-06 | 在途数据滞后（平台延迟 ≤1 小时） | 记录 `transitStale=true`，建议量标记「含未确认在途」 |
| PI-07 | 回读值与输入不一致 | 整批 `REJECTED`，不留部分通过 |

## 7. 输出契约

```json
{
  "schema": "purchase-inventory/suggestion/v1",
  "storeId": "400370",
  "asOf": "2026-11-10T12:00:00+08:00",
  "calibersUsed": ["inventory.actual","inventory.occupied","inventory.transit","sales.qty.total"],
  "calibersMissing": [],
  "params": { "window": 14, "leadDays": 25, "safetyDays": 10, "minOrder": 20 },
  "items": [
    {
      "skuId": "…",
      "verdict": "RESTOCK",
      "physicalAvailable": 0,
      "dailyVelocity": 0,
      "coverDays": 0,
      "suggestQty": 0,
      "reason": "人话一句，必须能独立读懂",
      "unknowns": ["在途数据滞后 40 分钟"]
    }
  ],
  "summary": { "restock": 0, "watch": 0, "overstock": 0, "deadStock": 0, "noHistory": 0 },
  "gate": { "required": true, "question": "…", "defaultIfIgnored": "stall" }
}
```

三条硬规则：
1. **`unknowns` 不许为空数组冒充确定**。真的没有未知，要显式写 `["无"]` 之外的空值语义，不能靠沉默。
2. **`reason` 必须是结论，不是数据堆砌**。合格：「覆盖只剩 8 天，低于 35 天补货线」。不合格：「actual=12, occupied=3, transit=0」。
3. **`gate.defaultIfIgnored` 只能是 `stall`**。与人无关的超时放行一律不允许。

## 9. 本版明确不做

1. **不算钱**。COGS 未核准（C3 未开工），任何金额输出都是编造。
2. **不提交采购单**。只出本地草稿，等人在 Gate 上点。
3. **不写平台**。库存与采购都在平台侧，本版零写入。
4. **不做选品**。该不该卖这个品不归它管。
5. **不清理库存**。`OVERSTOCK` / `DEAD_STOCK` 只标记，不产出任何降价或清仓动作。
