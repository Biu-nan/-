## 3. 顺带修掉一个 CLI 缺陷

现象：不传 `--event-root` / `--artifact-root` 时，CLI 报
`FATAL ERR_INVALID_ARG_TYPE The "path" argument must be of type string. Received null`。

根因（`DEBUG=1` 打 stack 定位到 `workflow.js:95` 的 `path.dirname(eventRoot)`）：
```js
function arg(name, fallback = null) { ... }
...
eventRoot: arg("--event-root", undefined),
```
**显式传 `undefined` 会触发默认参数**，`arg()` 实际返回 `null`，
于是 `eventRoot=null` 绕过了解构默认值 → `path.dirname(null)` 抛错。
直接调用 `runPurchaseWorkflow` 不经过 CLI，所以一直正常，掩盖了这个问题。

修复（`agents/purchase-inventory/src/cli.js`）：改成 `arg("--event-root") ?? undefined`，
把「未提供」显式还原成 `undefined`，让 workflow 的默认值生效。
同时给 CLI 的 catch 加了 `DEBUG=1` 时打印 stack（诊断改进，默认关闭）。

**回归验证**：原失败场景 `exit=0` / `WAITING_HUMAN` / 6 事件 / `VERIFIED`；
`--evals` 11/11 通过；`node --check` 通过；产物按 runId 分目录。

## 7. 修正 window 后：真实缺口超单批上限（2026-11-10 20:16）

### 7.1 修复
`decide.js:142` 的日均 = `sales.qty.total / params.window`，而 `params.window` 默认 14，
CLI 原先没有 `--window`。修复后优先级为

并显式把 `params` 传给 workflow（此前完全没传）。`--evals` 11/11 回归通过。

### 7.2 修正后的真实结论

`runId = pi-20261110-121544-351edf`，输入与 §1 相同（7d=742、historyDays=7）：

```
日均        = 742 / 7            = 106        （此前错算成 742/14 = 53）
physicalAvailable = 514 - 49 + 368 = 833
覆盖天数    = 833 / 106          = 7.86 天    （此前错算成 15.7 天）
补货缺口    = 106 × 35 - 833     = 2877 件    （此前错算成 1022 件）
```

结果 `status = BLOCKED`，4 事件（INTENT→DELEGATED→ACCEPTED→BLOCKED），
原因来自 `limits`：

```
{"reason":"QUANTITY_LIMIT",
 "detail":"QUANTITY_LIMIT 批次合计 2877 件超过上限 2000"}
```

**这不是故障，是约束正确生效**：真实缺口 2877 件超过单批 `maxTotalPerOrder=2000`，
workflow 拒绝给出不合规建议（fail-closed），而不是硬出一张超限采购单。

### 7.3 这是需要 Lance 决策的业务事项

400370 当前按 7 天日均 106 件、35 天补货线算，一次要补 **2877 件**，
已经超过你们定的单批 2000 件上限。可选：

1. **分两批下单**（2000 + 877），系统保持 fail-closed，人工拆单
2. **调高 `limits.json` 的 `maxTotalPerOrder`**（业务约束，需你改并说明理由）
3. **缩短补货线**（`leadDays + safetyDays` 从 35 降下来，减少一次备货量）

> 注意：7 天窗口容易被单日波动放大（742/7）。若改用 30d 平滑（2773/30=92.4），
> 缺口 = 92.4×35−833 = **2401 件**，仍超 2000。两种窗口都指向"要分批"。
