# 系统定位与成熟产品对照：讨论稿

日期：2026-10-25。状态：历史定位初稿已由《2026-10-25-confirmed-product-positioning.md》中的用户确认定位取代；案例与经营机制建议仍为讨论稿，不是已批准的架构设计或开发指令。

## 1. 用户最新要求与协作原则

用户要求顺序：定位 → 市场成熟案例 → 确定完整系统开发框架 → 确定开发闭环方案 → 开发计划。

用户澄清：Codex 与 WorkBuddy 共同开发，Codex 作为核心大脑统筹，优先使用 Codex 额度，不足时由 WorkBuddy 接续；WorkBuddy 参与思考和开发。不得继续解释成 WorkBuddy 仅为执行者，也不得把早期按模块固定分工草案当成双方已确认约定。自动额度监测、自动唤起和接续能力尚未验证。

当前阶段只研究与讨论，不据旧计划启动新开发。

## 2. 定位证据与边界

本轮读取来源：
- `.workbuddy/memory/2026-10-25.md`：WorkBuddy 对用户需求的转述，不等于原始逐字会话。
- `docs/SYSTEM_OPERATING_LOOP_v0.1.md`、`docs/SYSTEM_OPERATING_LOOP_v0.2.md`。
- `docs/SYSTEM_FRAMEWORK_v1.0.md`。
- `docs/superpowers/specs/2026-10-24-workbench-reliability-upgrade-design.md`。

WorkBuddy 记录中的需求演进：产品图驱动上品 → 对话驱动整个系统 → 商品全生命周期与店铺运营周期闭合 → 聚焦正在出单、衰退、新品机会、潜在风险，以增效为目的 → 回归整个系统框架，数据插件不是主线。

记录中提到 Anna 为业务对话入口，工作台承载可见执行，异步任务，正式发布保留人工决定。入口名称及未来授权边界需按用户最新诉求确认；此前的 P0–P6 规则及阈值不能全部视为用户亲自批准。

建议定位：**面向跨境电商经营者的 AI 经营工作台：围绕商品与店铺，把经营事实、诊断建议、授权执行、结果核验和复盘连起来，帮助用户以更少的重复劳动管理业务。**

“经营操作系统”可作为愿景简称，并非需要另造底层操作系统。首期内部自用/小团队、AliExpress Choice 优先来自此前方案，仍需确认是否扩展为对外产品或跨平台首发。

建议以人工投入、端到端完成率、错误/重复动作、异常处置效率衡量首期增效。利润等经营结果另作长期效果指标，不能直接把变化归因为 AI。

需区分两件事：产品中的经营助手是业务角色；Codex 与 WorkBuddy 是开发协作角色，开发时谁接续不决定产品运行时的架构。

## 3. 已核对的成熟产品对照

以下为官方产品文档支持的能力；没有对这些产品做本地试用、采购评估或独立效果审计。相似度与借鉴建议是 Codex 判断，非厂商结论，也不代表任一产品已完整覆盖用户场景。

### Shopify Sidekick + Flow：对话与工作流

Sidekick 根据店铺数据提供帮助，提交变更供用户审核，可规划多步任务并在后台继续工作；Flow 用触发器、条件、动作和连接器组织重复工作。

借鉴：自然语言进入实际业务流程，执行状态可见，持续任务不依赖聊天窗口一直打开。边界：官方能力以 Shopify 环境为中心，不能据此断言直接兼容现有 Choice、店小秘和浏览器链路。

来源：
- https://help.shopify.com/en/manual/ai-powered-tools/sidekick
- https://help.shopify.com/en/manual/shopify-flow/reference

### 领星 ERP：跨境经营业务结构

官方帮助中心覆盖产品、销售、采购、仓库、财务、统计及 BI。全平台补货建议结合销量、库存、在途、采购单据生成建议，并支持生成采购单或采购计划。2026 年 7 月更新列有 AI 数据分析。

借鉴：商品、SKU、店铺、库存、采购与经营分析之间的业务关系；从分析建议落到具体单据。边界：平台、仓配模式和字段口径有差异，FBA 规则不能直接搬到 Choice。

来源：
- https://www.lingxing.com/help/index
- https://www.lingxing.com/help/article/allPlatformReplenishmentAdvice
- https://www.lingxing.com/help/article/Update273

旧文档中的“ERP 只管执行，BI 才能决策”“ERP 因为 OLTP 所以利润永远算不准”属于过度概括，不应作为架构依据。实际应区分业务能力、计算方法、数据质量与职责，而不是按产品类别作绝对判断。

### Palantir Foundry / AIP：事实、业务对象、行动与治理

官方文档描述以 Ontology 连接业务数据与 AI 工作流，并提供权限、审计和人工审批。官方 General Mills 案例介绍 ELF 在供应链约束、容量、成本等信息基础上给出应对中断或降本建议。

借鉴：让 AI 对具体业务对象提出可追踪的行动，通过权限和审核控制执行，并保留决策依据。边界：这是企业级架构参照，不能据案例推断我们需要同等规模、复杂度或预算；案例效果为厂商材料，本轮不承诺类似收益。

来源：

- https://www.palantir.com/docs/foundry/aip/ethics-governance

## 4. 后续讨论的交付物与顺序

1. 定位说明：服务谁、解决什么、成功标准、第一期边界。先由用户校准。
2. 案例对照：能力、业务适配、可借鉴内容、不可直接复制的部分。
3. 完整系统框架：业务范围、用户入口、核心对象、事实来源、决策与执行边界、权限、恢复、监控、现有功能如何保留。先比较可行路线再定设计。
4. 闭环方案：分别定义经营闭环、系统运维闭环、开发交付闭环；每一步写清输入、产出、核验依据、责任、异常去向。
5. 开发计划：在框架与闭环确定后，才拆分可验收任务、依赖、当前负责人、影响文件、检查方式、回滚与交接点。

不得将本节顺序表当成已完成的框架或详细开发计划。也不因研究定位而推翻现有代码、替换技术栈或直接开始重构。

## 6. CEO Agent 经营机制建议（未批准）

用户要求 CEO Agent 的运营逻辑与行动像现实 CEO 或电商运营总监。本节为针对该需求的设计建议，不声称 AI 已具备成熟经营能力或会保证利润。

### 职责与决策过程

- 用户确定经营目标、约束和重要取舍；Agent 把目标分解为可检查的经营计划。
- 每次经营循环：读取目标与历史决定 → 检查经营事实的时间、口径与完整度 → 识别机会/异常 → 检验原因假设 → 比较行动、暂缓与继续调查 → 按影响、紧迫性、可信度、资金和执行成本排序 → 建立有边界的任务 → 经 OS 执行与回读 → 到约定时间复盘效果。
- 不预设一个虚假的统一收益分数。证据不够时先调查；无变化且无待处理事项时可以结束巡检。
- 每个行动应带目标、对象、依据、选用方案及理由、授权/预算、完成标准、效果观察期、停止条件和后续责任。
- 任务完成与经营有效分开记录：草稿保存成功不等于正式发布；发布成功不等于转化改善；销量变化不直接证明措施有效。
- 决策记录应包含当时已知事实、假设、选择理由和结果，保存于共享业务系统。无须保存模型私有推理过程；更换对话入口后仍能接续。

### 建议的组织方式

一个对外负责的经营角色，内部区分目标与资源管理、店铺日常运营、具体业务执行三类职责。优先复用现有工作流与工具；不因“像公司”而先建立多个常驻部门 Agent。

两种可行路线：规则驱动运营总监（稳定但处理新问题能力有限）；在业务与预算边界内自主分析和编排的 CEO（更贴合用户目标，但需更强的证据、效果评估和接管机制）。建议后一种管理方式配合可验证的工作流执行，具体方案待讨论。

节奏建议：日常发现和跟进、每周效果复盘、周期性资源/商品组合调整，辅以重要事件触发。频率与时间未确定，本轮不创建自动任务。

### 例子：核心商品销量下降

先检查数据口径、可售状态、库存、曝光、转化、价格与近期变动；不能仅凭销量下降直接改图或降价。确认原因后，选择调查、恢复供给、内容试验或其他适用行动。在 OS 创建受控任务并核验实际执行；保留基线及观察期，再评估继续、调整或停止。缺失利润/现金数据时不得据此给出确定的财务决策。
