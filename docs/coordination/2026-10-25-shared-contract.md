# 共同目标与协作合同 v0.1

状态：Codex已整理，待WorkBuddy回执。目标是对齐一套框架与接口，保留现有业务，不重写一套系统。

## 1. 用户已直接明确的要求

- 系统从约6.5分向9.5分升级，分数必须有实际验收证据，不提前宣称达标。
- 升级前保存代码到GitHub私有仓库并留回滚机会。
- 先判断目标、验收、约束；最小改动；保护已有功能；不擅改核心结构、不删数据、不重构无关模块。
- 事实可验证；未运行测试就明确未运行；未知事项标待确认。
- 先同步双方思路、进度和用户理念，再协作；避免重复实现和相互覆盖。
- 每次执行报告交代目标、完成、范围、验收、风险及Backlog。

## 2. 从WorkBuddy记录提炼的业务理念

来源为WorkBuddy本地文档与2026-10-25记忆，属于对方对用户意图的记录，尚未由双方重新确认：

- 主线是整个运营系统框架；经营抓取、分层和报表是插件，不能让主线再次变成无限补数据。
- 用商品完整生命周期和店铺日/周/月运营周期组成双环，由对话入口协调。
- 对话和网页读取同一权威状态；不能各自编一份进度，也不能再造平行状态真相。
- 经营事实可追溯、口径明确，缺失用null与reason表达；派生指标可以重算。
- 人工输入、歧义和审批是正常工作状态，默认等待，不超时自动放行。
- 衡量实际增效：能识别在做什么、卡在哪里、需要谁决定、如何核对执行后果。

本合同不把WorkBuddy文档中的行业判断、阈值或“自动批准10行”等建议变成用户已批准规则。

## 3. 两条开发线合成一条路线

| WorkBuddy路线 | Codex路线 | 接缝约定提案 |
|---|---|---|
| F1：只读WorkUnit总账和面板 | W2：原存储安全读写 | 保留F1适配器；不得把只读投影变成另一套写状态。坏源显示异常，不覆盖原件 |
| F2：Capability Registry | W3：登录身份、角色、对象范围 | 能力声明与访问授权分开；登记为能力不等于获得调用权限；角色/操作者以服务端身份为准 |
| F3：Gate与事件 | W4/W7：任务事实、版本审批和外部动作 | 只实施一套审批消费与事件写入流程；Gate显示与审批记录相连，不分别建立两个可放行令牌 |
| F4：决策策略建任务 | W4：持久任务和输入快照 | 决策产出任务建议；运行Job是迁移场景的权威状态，WorkUnit为统一视图。写入所有权迁移前明确，禁止双向双写 |
| F5：对话控制层 | W5/W7：资源锁、外部写入与核对 | 对话/网页调用同一授权执行路径；同一浏览器资源串行；结果未知先核对，不重新创建 |
| 经营facts及商品分层 | W8/W9：质量、回归和受控试运行 | 数据口径规则由WorkBuddy维护；质量/权限/恢复分别验收，不把抓到数据当作整个框架已完成 |

补充：经营事实存储、任务事务状态、只读投影属于不同数据域。可以保留不同载体，但每个域/每个工作流必须说清唯一写入权威，不能用append-only经营facts替代任务事务。

## 5. 必须先明确的四个边界

1. F1总账已交付，Codex不重做；W4未来Job迁移必须继续服务现有总账，不替换当前业务表。
2. P0–P6是副作用等级；经营告警P0/P1是优先级，字段不能混用。注册表的描述性级别不能冒充真实鉴权。
3. F2草案中的小批量autoApproveWithin只是候选。没有用户明确的范围授权，不因行数少或等待超时自动批准。已有明确授权继续有效；不重复向用户请求相同批准。
4. 旧发布链路和新能力注册表不可因“已注册”就标可执行；planned/unverified保持不可自动执行。真实外部试跑、生产重启和数据迁移按具体授权与验收安排执行。

只读不等于可以公开读取：F1状态、图片和经营资料仍需W3认证/范围控制。当前接口核对通过不能用来宣称已完成权限隔离。

task_id、实现主责、工作目录/分支、base commit、目标、非目标、允许修改文件、不得修改文件、消费/产出接口、状态来源、实际验证命令与结果、提交/产物、未完成和下一步。
