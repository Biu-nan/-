## P0-1 · 新增 §5.4「经营判断力：五个决策案例与授权边界」

> 建议整段插入 §5.3 之后。这一节回答用户原话"怎样像现实公司里面的 CEO 一样或者电商运营总监一样"。
> §5.2 的 8 步流程是**判断的执行顺序**，本节是**判断的内容与边界**。两者不可互相替代。

### 5.4.1 判断力的三层结构

| 层 | 谁负责 | 错了会怎样 |
|---|---|---|
| L1 事实判定 | OS（口径、新鲜度、覆盖率） | 用错口径 → 后面全错（已发生：`sellableQuantity` 差 400 倍） |
| L2 选项生成 | CEO Agent（至少给 3 个选项，含"不做"） | 只给一个方案 = 没做判断 |
| L3 取舍准则 | 本节 5.4.2 + 5.4.3 | 没有准则就变成凭语气选方案 |
| L4 上交判定 | 本节 5.4.2 的授权矩阵 | 该问的不问 = 越权；不该问的问 = 瘫痪 |

**硬规定：任何决策记录必须至少含 L2 的 3 个选项（其中一个是"暂不处理"），否则该决策视为不完整，不得进入执行。**

### 5.4.2 取舍准则：可逆性 × 时效窗口（本补丁的核心机制）

"像 CEO 一样判断"不能是形容词。把它压成一条可执行规则：**动作的授权级别由「可逆性」和「时效窗口」两个维度决定，而不是由金额或感觉决定。**

| 动作类型 | 可逆性 | 时效窗口 | 授权级别 | 谁定 | 例子 |
|---|---|---|---|---|---|
| 只读采集、诊断、生成建议 | 完全可逆 | 无 | **P0–P1 自主** | CEO Agent | 抓数、分层、诊断、写建议 |
| 改本地内容（标题/描述/图 Prompt） | 可逆（本地） | 小时级 | **P2 自主** | CEO Agent | 重写标题、重出图 |
| 改平台草稿态 | 可逆（未发布） | 小时级 | **P3 报备** | CEO Agent 做，OS 留痕可见 | 存草稿、改 SKU 映射 |
| 影响价格心智的动作（改价/投流） | 可逆但**有观察期成本** | 天级 | **P3 报备 + 观察期锁定** | CEO Agent 做，用户事后可撤 | 调价、开流量智投 |
| 不可逆动作（发布上架/砍品/清仓/删除） | **不可逆** | 天级 | **P5–P6 必须人批** | 用户 | 上架、下架、清仓 |
| 涉及现金（采购/加预算） | 半可逆（可退但有时限） | 小时–天 | **人批 + 金额阈值** | 用户 | 补货、加投流预算 |
| 改目标/授权/预算上限 | 结构性 | — | **永远人批** | 用户 | 改月度目标 |

三条推论（建议写进蓝图）：

1. **"可逆 + 小时级"的动作不该问用户**——否则每天几十次确认，用户会开始无脑点"同意"，审批就失效了。
2. **"不可逆"的动作不许因"等太久了"而放行**，与蓝图 §8 的"等待不是批准"一致。
3. **同一动作在不同情境下授权级别会变**：正常期调价 = P3 报备；大促期调价 = P5 人批（因为可逆性降低、影响放大）。**授权级别必须绑定"情境版本"，不能只绑动作类型。**

### 5.4.3 五个决策案例（全部使用本项目 2026-10-25 实测数据，非虚构）

> 说明：数字来自 `data/metrics/` 与 `stratify-products.mjs` 当日输出；案例用于展示**判断结构**，不是建议立即执行这些动作。

#### 案例 1 · C2 假死品：砍 / 复刻 / 补货

- **情境**：某 C2 层商品，累计出 174 件，近 30 日销量 0、库存 0、无动销。分层引擎把它归为 C2（长尾）。
- **可用证据**：累计销量 174（证明曾验证过需求）、当前零库存、近 30 日零动销、实仓数据覆盖（该品有实仓记录）。
- **三个选项**：
  - A 砍掉（清 listing）：省管理成本，损失潜在复购与历史评价权重
  - B 复刻（同款再上，换主图/标题）：成本 1 次上品，成功率未知
  - C 补货（按历史 174 件节奏小批量）：占用现金，若需求已衰退则压货
- **默认判断规则**（可争论，非定论）：累计销量 ≥ 50 且近 30 日 = 0 且库存 = 0 → **优先 B 复刻**，不选 A 也不选 C。理由：174 件证伪了"没需求"，零动销是"没货"造成的而非"没市场"；C 需要现金且需求时效未知。
- **反例（什么时候这条规则错）**：如果该品历史销量集中在某次大促单点，平时本就零动销 → 复刻也是零动销，应选 A。
- **上交条件**：若复刻需新拍照/新开模（成本 > 阈值）→ 升级为用户决策。

> 这条案例的价值：**它纠正了一个真实差点发生的错误**——该品当时被分层引擎当成"长尾可清理"，实际是"假死"。

#### 案例 2 · S 层断货倒计时：加急 vs 降权

- **情境**：S 层 2 个商品库存仅剩 9–11 天可售；S 层 4 个商品合计扛 31.7% 销量。
- **三个选项**：
  - A 加急采购（成本 +30%）：保住销量与排名，牺牲毛利
  - B 降权/限量（人为压低曝光）：保排名权重不崩，损失这 10 天的销量
  - C 不处理：等自然断货（断货会伤搜索权重，恢复慢）
- **默认判断规则**：断货天数 < 采购前置期 且 该品贡献 > 层均 → **A**；若断货天数 < 3 天（来不及）→ **B**；若该品毛利 < 15%（加急后亏损）→ 上交用户。
- **反例**：若该品正在被竞品以价换量、本身在衰退期 → 加急采购只是延后死亡，应选 B 并准备替代品。
- **上交条件**：加急采购金额超单笔阈值；或该品同时是活动报名商品（承诺冲突）。

#### 案例 3 · 发布失败 9 个（失败率 3.90%）：重试 / 查根因 / 忽略

- **情境**：店小秘侧 `publishFail: 9`，失败率 3.90%（WARN 级）。
- **三个选项**：
  - A 直接批量重试：最快，但若根因是模板/字段问题会重复失败并放大错误
  - B 先抽 1 个查根因再决定：慢 1 小时，但避免 9 次无效写入
  - C 忽略：9/231 占比小，但失败件里有高价值品时不可接受
- **默认判断规则**：失败率 > 2% 且失败件含 S/A 层 → **B 必选**；纯 C2 且失败率 < 5% → 可 A。**任何情况下"直接批量重试"不得在未读错误原因时执行**（与蓝图 §10「外部提交超时不得立即重复提交」同源）。
- **反例**：根因是平台侧临时故障（已知公告）→ 等待后 A 是对的。

#### 案例 4 · 未上线积压 248 个：先筛 vs 全量上

- **情境**：草稿 210 + 待发布 38 = 248 个未上线积压。
- **三个选项**：
  - A 全量批量上：产能最大，但会把未验证的品全部铺出去，拉低店铺整体转化与动销率
  - B 先按分层筛（只上 S/A/B 候选）：少上 80%，但每件质量可控
  - C 先做 3 个样板（含完整证据链）再决定节奏
- **默认判断规则**：店铺动销率低（< 40%）时 → **B**；系统首次跑通某个新流程时 → **C**；动销健康且流程已验证 → **A**。
- **反例**：若积压件中有硬截止（活动报名要求提前上架）→ 硬期限优先于质量筛选，但仍需最小证据。

#### 案例 5 · 什么时候"不做"才对（最重要的一条）

- **情境**：北京时间 15:00–17:00 平台日切窗口，实测店铺页 pv 从 3194 掉到 4，而 30 日销量仍为 2235（物理矛盾）。
- **正确行为**：**系统拒绝出经营结论**，标注 `SKIPPED_PLATFORM_DAYCUT`，等 17:00 后重跑。
- **错误行为**：用归零数据算"流量暴跌 99%"→ 触发"救店"动作 → 花掉真实预算救一个不存在的火。
- **推广成通用规则**：**数据新鲜度不满足时，"不做判断"本身就是一个必须被显式记录的正确输出**，而不是"暂停"或"重试"。
- **反例**：硬截止任务（活动报名今天截止）不受此限，但必须在结论里标注"基于非最新数据"。

### 5.4.4 「不知道」的表达规范

建议明确规定三档输出，禁止混用：

| 档位 | 何时用 | 必须附带 |
|---|---|---|
| **可执行结论** | 证据充分、口径明确、新鲜度合格 | 依据 + 选项 + 授权级别 |
| **条件结论** | 证据部分缺失 | 缺什么 + 补齐路径 + 补齐前不做什么 |
| **拒绝判断** | 数据不可用 / 口径冲突 / 日切窗口 / 权限不足 | 拒绝理由 + 何时可重试 + 谁可解锁 |

**禁止：把"条件结论"写成"可执行结论"，或把"拒绝判断"写成"系统暂时不可用"。**

## P0-2 · 新增 A13「经营效果验收」+ 反作弊条款

> 建议补在 §13 验收矩阵 A12 之后。

### A13 · 单一动作的经营效果可判

| 项 | 要求 |
|---|---|
| 对象 | 一个固定 SKU（非店铺汇总） |
| 动作 | 一个明确动作（改主图 / 改标题 / 调价 / 补货），有执行时间戳 |
| 观察期 | **≥ 7 天**，且执行前后等长 |
| 口径 | 必须显式声明，取自 `config/metrics-schema.json`：`sales.qty.total`（含货通）/ `sales.qty.direct`（不含货通）/ `sales.amount.settle`（结算）——**三者同店同期可差 36 倍（实测 2302 vs 64），不钉死口径任何结论都可被"证明"** |
| 对照 | 同期店铺整体基线（用于剔除大盘影响） |
| 干扰因素 | **必须列出**：活动、竞品调价、断货、平台规则变更、季节性 |
| 结论档位 | 改善 / 未改善 / 证据不足 —— **"证据不足"是合法结论，不得为了好看而写成"改善"** |

**反作弊条款（建议写入 §13 末尾）**：

1. 观察期一旦登记不得缩短；需要改必须新建一条 Review，保留旧记录。
2. 复盘时不得更换口径（换口径 = 换考题）。
3. 不得用"任务完成率"代替"经营效果"，两者必须分栏报告（与 A10 一致）。
4. 效果为"未改善"时，必须保留原决策记录，不得删除或改写。

## P1-5 · §8 建议降级：从"分布式并发"改为"会话串行"

**依据（INFERENCE，基于实证）**：ChatGPT Work 与 WorkBuddy 实测运行在**同一台机器、同一个 Chrome（CDP :9223）**上，6 个标签同属一个浏览器实例。

因此真实风险不是"两个分布式执行者的写冲突"，而是：

1. 同一时刻只有一个对话在驱动，另一个看到的是**过期上下文** → 需要**上下文版本校验**，不是分布式锁；
2. 两者会抢**同一个 composer / 同一份 `run-state.json`**（已踩过：双实例抢端口、模型菜单被另一窗口重置）→ 需要**单执行体互斥**；
3. 真正的跨进程并发只存在于 **OS 后台任务 vs 前台对话**，那才是需要占用/版本检查的地方。

建议保留 §8 的"唯一操作标识 / 结果未知先核对 / 审批绑版本"三条，**删掉"有限期占用"的分布式语义**，改为"单一前台执行者 + 后台任务占用声明"。
