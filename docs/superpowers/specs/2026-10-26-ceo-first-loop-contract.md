# 首店经营闭环契约 v0.2

2026-10-26。用户已确认首店与经营目标；本稿承接详细闭环及 P0 实测。真实口径/期限的未确认项只阻塞依赖动作，不阻塞隔离机制开发。

## 1. 用户目标与证据

- 首店：纳物-箱包全托1店，现有环境 ID `400370`。该 ID 来自当前本机脚本映射，不当成平台通用店铺 ID；channelId 的当前有效性需采集时再核对。
- 用户原话：**“完成日出200单 要求且月净利润在12000”**。
- CEO 必须同时追踪两项目标。不得通过亏损冲量宣称整体达成，也不得用利润达标掩盖订单目标未达。
- 用户随后确认：“每日支付商品件数”；“在12月一个月达到 是的 扣除经营成本后（不含品质罚款）”。据当前日期将目标月份记录为 **2026 年 12 月**：每日支付商品件数至少 200 件，12 月经营净利润至少人民币 12000，扣除经营成本、不含品质罚款。年份按当前会话日期解释，不外推为每年重复目标。
- 目标范围为 2026-12-01 至 2026-12-31；用户时区 Asia/Shanghai。平台原始日界线如何映射仍需实际核验，不把源数据的 PDT/PST 标签当固定偏移。
- 不擅自把每天达标改为月均达标，不把一次达到当成持续达标；连续观察天数待初始化确定。
- 本稿不对达成概率、所需资金或完成日期作未经数据支持的承诺。

当前目标对象建议 ID：`goal-store-400370-20261026`，初始版本 1。该 ID 是拟定业务标识，目前尚未写入产品数据库；未确认字段应以显式 pending 保存。

## 2. 测量契约

| 目标 | 已确定 | 缺失与判定规则 |
|---|---|---|
| 每日支付 200 件 | 数值至少 200，单位件，店铺范围已定，2026 年 12 月每天追踪 | 当前字典 sales.qty.total 为含货通支付件数，作为全店目标首选数据口径；必须核验该店覆盖率、源日界线和退款处理。不得以订单数或不含货通 direct 值直接替代 |
| 12 月经营净利润 12000 | 至少 CNY 12000，2026 年 12 月自然月，扣经营成本但不含品质罚款 | 完整成本及归属期仍需对账。sales.amount.net 仅平台净收入，不能替代该自定义利润指标 |
| 同时满足 | 两个目标都要检查 | 任一口径、数据覆盖或成本缺失，则整体达成状态为无法判断，不默认失败或成功 |

净利润的成本核对清单应至少逐项确认采购货值、平台扣费、履约/物流、包装、广告、退款售后及适用的固定费用分摊是否计入、金额和归属期。用户已明确品质罚款不计入目标利润费用，须单独列示实际罚款或“待取数”。若以平台净收入为起点，只有证明其中已经扣了品质罚款，才可对同归属期金额加回；没有证据不得机械加回。其他已扣费用不能重复扣除；采购现金支付与已售商品成本不得直接等同。此为经营指标契约，不擅自决定税务/会计规则。

对所有输入保存 storeRef、来源、统计事件、窗口、时区、单位、覆盖率、采集时间和口径版本。未知值不填 0。只有上述数据契约成立后才计算差距、趋势和预测。

## 3. 第一条纵向场景

经营巡检 → 找到一个有证据的问题 → CEO 比较处理与暂缓选项 → 形成可执行业务任务 → 已验证能力或人工处理 → 回读核验 → 日终复盘 → 次日调整。

具体问题从首店可用数据中选择，不预设当前一定缺货或内容有问题。目标口径不足时，第一项必要工作是取得合格事实/补齐口径；该工作完成不能被算成订单或利润目标达成。

近期可交付的 P1 是“真实只读简报 + 可验证 CEO 决策单 + 容量内的今日草案”。草案不得自动入执行队列，也不冒充完整经营闭环。P2 才接审批、任务写入与执行回执；P3 接日终自动推进与入口接续；P4 观察经营效果。

## 4. 决策与排程边界

决策记录绑定目标、事实版本、策略版本、业务对象、备选及选择理由、证据强弱、停止条件和复盘时间。仅要求有意义的可行备选，不强行凑三项。外部 CEO 形成决策，OS 校验引用、范围和约束，不把硬编码模板输出冒充真实模型经营判断。

目前未确认授权额度；新经营动作默认只读/草案。已有其他流程的具体授权仍按其原有效范围适用，不能泛化到本目标。目标及币种已明确，但缺完整成本时仍可做调查，不能形成“利润足够可降价”的结论。

P1 草案的候选运行上限：单次至多 20 个候选业务任务、60 秒本地处理、最多 1 次同目的外部 CEO 决策请求；超限返回明确停止原因。它是首版可配置工程上限，不代表用户的人力容量、购买授权或承诺所有产品都能强制控制宿主额度。2026-10-26用户已确认首店1人、每日总容量300分钟，其中60分钟应急预留，常规任务预算240分钟。受控goal版本升为2；旧120/30仅保留为已被替代的历史试算。容量确认不代表经营事实、任务耗时或动作授权已核准。

## 5. 权威状态与存储归属

| 对象 | 后续存储/入口 | 边界 |
|---|---|---|
| 首店目标版本 | 既有 SQLite 文件中拟增 ceo_goal_versions | 不用 platform net 代替利润；目标确认是单独授权操作，不能让普通草案保存接口伪造确认 |
| 事实引用 | 现有 metrics facts/raw + 引用摘要 | 不复制成另一套财务事实；原始数据不进源码仓库 |
| 决策版本 | 同库拟增 ceo_decision_versions | 绑定事实/策略版本，修改不覆盖原记录 |
| 日计划版本/候选任务 | 同库拟增 ceo_plan_versions，tasks_json 保存草案 | P1 不创建可执行任务、不派发平台写入 |
| 现有执行任务/尝试 | 继续引用原流程 ID；迁入前明确来源与迁移版本 | 禁止两套服务同时推进同一旧任务；采集任务不是通用经营任务 |
| 人工跟进 | 复用 DailyOperationService 待办；完成后仍须核验 | resolved 不自动等于平台动作已完成 |
| 新执行证据/审批 | P2 实施计划定义同库版本/回执存储与命令接口 | 没有核验载体前不开新执行入口 |

SQLite 文件沿用 `data/charm-listing-workspace.sqlite` 的既有持久载体，但新增对象与原 charm 商品表解耦，不将经营巡检伪装成挂件 Listing。以上是后续设计，不是本轮建表；P1 先完成纯契约与草案机制，落库任务另有审批/原子性测试后实施。

P1 不增加第七套独立执行器。P2 要使迁入的新经营任务只有一个权威写入服务，旧工作流由适配器引用和受控调用；未迁入部分保持原有责任，不能声称整个系统状态已经统一。

## 6. 旧状态映射

| 来源实际状态 | 统一业务展示 | 规则 |
|---|---|---|
| 草案/尚未批准 | 草稿或待决 | 不进入执行 |
| APPROVED/READY | 就绪 | 仍检查实际授权、输入及资源 |
| PUBLISHING/PENDING_OPERATOR | 等待人工或待核验，按真实尝试区分 | 不是发布完成 |
| VERIFYING 或超时未知 | 待核验 | 先对账，不直接重发 |
| LIVE/明确成功回执 | 已核验完成 | 须匹配同一店铺/对象/动作，不能只认名称 |
| resolved 人工待办 | 人工步骤已报告，效果待核验 | 不把待办勾选当作外部执行证据 |
| 旧七态投影缺待核验态 | 保留原 state，加业务细节说明待核验 | 后续明确版本化展示，不映射 DONE 以求兼容 |

## 7. 连接与实施边界

实际工程会话可 GET 当前 OS；目标经营入口尚未回读确认。WorkBuddy 配置中的 commerce-os 指向 E 盘 Supabase 项目，与 F 盘本机状态不是同一事实源；保留它，不自动改名/迁移/合并。

首选最小连接验证：提供本地只读简报命令，目标经营会话实际执行并返回 schema/时间/对象信息；可用后沿同一服务加适配。不能因为独立命令测试通过就宣称 WorkBuddy 已调用。无用户消息自动唤起仍单独验证。
