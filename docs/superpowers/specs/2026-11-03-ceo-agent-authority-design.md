# CEO Agent 权威与有效性设计 v0.1

2026-11-03 · **待审定 · 非开工指令 · 不代表任何验收通过**

> 本文回答三个问题：CEO Agent 为什么能"权威"、怎样才能"有效"、如何适配 Lance 的一人跨境运营现实。
> 顺序遵循 Lance 指定：**先对齐目标 → 再对清现实 → 才谈设计与开发**。

> 权威从属：业务定位 → `docs/coordination/2026-10-25-confirmed-product-positioning.md`；
> 经营闭环 → `docs/superpowers/specs/2026-10-26-ceo-os-operating-loop-design.md`；

## 0. 八条摘要（只看这一段也能执行）

1. **权威 ≠ 权限。** 权威来自"可追责 + 可复现 + 敢说不知道"。给足权限但判断不可复现的 Agent，第三次就会被无视。
2. **授权的正确切法是三档 A/B/C**，不是"重要/不重要"。A 档要宽到吃掉 80% 的动作，C 档要窄到只剩 7 条白名单。
3. **目标不是"日均 200 件"，是"约束下单位时间净利增量最大"。** 这两个目标函数推出的日常动作完全不同。
4. **现实很硬**：254 条路由全在"手"上，采购/库存/财务/售后 4 个域零实现，无决策记录、无复盘记录、无假设库——**有手，还没有脑和记性**。
5. **`config/metrics-schema.json` 已经写了 calibers/freshness/forbidden，但全仓代码对其引用数为 0。** 字典已写、口径未强制——这是当前最大的"平行真相"风险。
6. **成长的载体不是模型，是「经营假设库」。** 换模型它还在；模型不会因为用得多而变强。
7. **建议采纳率 100% 是危险信号，不是好信号。** 健康区间 60–80%。
8. **不做**：通用对话机器人、Temporal/LangGraph、8 个 Agent、未授权自动发布、销量预测。

## 1. 第一步：框架对齐目标

### 1.1 目标不能只有数字，否则会优化错东西

已确认的北极星：首店 400370 在 2026-12 日均 ≥200 件、月净利 ≥¥12000；3 店各 80 单/日。

但把"日均 200 件"直接当目标函数会立刻出错——**200 件低毛利单可能不如 120 件高毛利单**。项目记忆里的真实数字已经证明这一点：销售管理支付件数含货通、商品分析不含，同店同期 2302 vs 64；`sales.amount.net` 不是净利润，不含采购/头程/包装。

**所以真正的目标函数是：**

> 在「不出事」的前提下，最大化 **每小时人工投入换来的净利增量**。

三个约束是硬约束，不是优化项：
- **工时**：Lance 每周可用小时（唯一不可扩容资源）
- **现金**：备货占用 + 平台账期
- **账号安全**：任何单点风险不得越过毁店红线

这个目标函数直接推出三条与直觉相反的结论：
- 时间比钱贵 → 花钱省时间（工具/外包）通常是对的
- 低贡献订单要主动放弃 → "件数"和"净利"会打架，必须显式选
- "不出事"优先于"做得更多" → C 档授权必须极窄

### 1.2 目标 → 过程指标树（沿用 v0.2 术语，不新造词）

| 目标 | 拆解公式 | 可控过程指标（今天能推动） |
|---|---|---|
| O1 日均 200 件 | 曝光 × 点击率 × 转化率 × 件单 | 在架 SKU 数 · Listing 完整度 · 关键词覆盖 · 评价数 · 活动位 · 主图 A/B |
| O2 月净利 ¥12000 | GMV × 毛利率 − 固定成本 | 单件贡献 · 退货率 · 平台费率 · 广告占利比 · 头程单件成本 |
| O3 3 店各 80 单 | 单店模型 × 可复制性 | 模板复用率 · SOP 覆盖步骤数 · 新店冷启动天数 |

**硬规则**：任何进入执行队列的任务，必须能指向至少一个过程指标。指不到的，不是经营任务，是杂事，不进 Taskboard。

### 2.2 七个 Workflow 的诚实成熟度

| Workflow | 诚实评级 | 依据 |
|---|---|---|
| 上新与优化 | **L3** | listing-engine + contract + template + batch，链路最完整 |
| 选品与验证 | **L1** | 有服务，但验证/决策闭环未见 |

| 售后与体验 | **L0** | 无服务 |

> **7 个 Workflow 里，1 个 L3、2 个 L1、4 个 L0。** V0.2 把它们画成等权重，实际差距是 3 个量级。

### 2.3 三个真正的缺口

不是"缺 Agent"，是这三样：

1. **缺"脑"** —— 没有决策记录。CEO Agent 做的每个判断不留痕，就无法追责、无法复现、无法变聪明。**没有决策记录的 CEO，本质是一个记忆只有 7 秒的顾问。**
2. **缺"记性"** —— 没有假设库、没有复盘、没有失败案例。模型每次从零开始，用户每次重新解释业务。
3. **缺"口径强制"** —— 字典存在但零引用。Agent 读的仍是原始字段，所以必然算出 2302 和 64 两个都"正确"的数字。

**结论：现在的系统是很强的"手"，但没有"脑"和"记性"。补脑不是补 Agent 数量，是补记录结构与判断纪律。**

## 3. 第三步：CEO Agent 设计

### 3.1 权威悖论（必须先承认）

一人公司里的 CEO Agent 天然左右为难：

- 什么都要问 → 它是秘书，Lance 还是瓶颈，等于没解决
- 什么都能定 → 它会犯错，而且 Lance 不知道为什么错，信任一次性崩塌

**破局点：权威不来自"它能决定多少"，来自"它的决定事后能被检验"。**
一个会说"我基于这三条证据、排除了这两个可能、如果 7 天内 X 没发生我就认错"的顾问，比一个永远自信的顾问权威得多。

### 3.2 关键资产：已有的 `secretary-model.js` 原则

它已经确立了四条正确的边界，**CEO Agent 应当继承而不是重写**：

| 已确立原则 | 扩展到 CEO 的含义 |
|---|---|
| 模型只编译意图，不执行动作 | CEO 产出「决策草案」，执行仍由确定性代码/人完成 |
| 不写业务数据、不直接改状态 | CEO 不能直接改库，只能提申请 |
| 风险等级只能抬高，不能降低 | 模型判断为高风险时，任何下游不得降级 |
| 模型挂了就降级到本地占位 | CEO 不可用 → 系统退化为规则模式，不装死 |

**升级点只有一处**：秘书编译"用户想干什么"，CEO 需要编译"**当前应该干什么**"。前者是翻译，后者是判断。判断必须有记录。

### 3.3 三档授权（A / B / C）

授权不是一个总开关，是按「可逆性 × 金额 × 影响面」分档。**且必须白名单化，不写"重大事项"这种模糊词。**

**A 档 · 自己做，事后报备**（内部、可逆、无外部副作用）
- 采集数据、生成 Listing 草稿、建立任务、调整内部优先级
- 生成日/周计划、标注异常、关闭已完成的观察项、更新假设库
- **目标：吃掉 ≥80% 的动作量。A 档不宽，CEO 就还是秘书。**

**B 档 · 自己决定，事前一句话通知**（有外部副作用但**必须有后悔药**）
- 改自己店内标题/主图/描述（不涉价格）
- 调价幅度 ≤ 阈值且不低于成本线
- 报名符合条件且在预算内的活动
- 额度内的补货数量建议转采购单
- 非核心 SKU 上下架
- **硬门槛：无可回滚方法的动作，一律不得进 B 档。**

**C 档 · 必须停下来问**（白名单 7 条，不扩）
1. 首次真实发布上架到平台
2. 任何付款、采购下单、供应商合同
3. 调价超阈值，或低于成本线
4. 删除商品 / 关闭店铺 / 下架核心 SKU
5. 动账号设置、支付、物流模板、API 凭据
6. 接入新平台 / 开新店
7. 改目标、改截止时间、改口径定义

> **C 档是"信任的生死线"。** 该问没问一次，Lance 就会永久降低对它的信任，且很难恢复。所以 C 档宁可误问，不可漏问——**这一档允许"过度谨慎"，其他档不允许。**

### 3.4 让权威成立的四个机制

**机制一：决策必须留痕且可复现**

每条 Decision 至少包含：
```
对象 / 输入事实（含版本与抓取时间）/ 备选方案（含"不做"）
选择理由 / 排除理由 / 预期结果 / 失败条件 / 复查时间 / 置信度
```
标准：**Lance 拿同样的输入，能复算出同样的结论。** 做不到的不算决策，算猜测。

**机制二：必须能说"我不知道"**

建议分三级，界面上必须标色，**低级不得进执行队列**：

| 级别 | 含义 | 处理 |
|---|---|---|
| 已验证 | 有本项目实测数据支撑 | 可进 A/B 档 |
| 有依据未验证 | 有行业常识/外部资料，未在本店验证 | 只能进「小范围试验」 |
| 推测 | 无支撑，属结构化猜测 | **只能进讨论，不得进队列** |

> 一个从不承认不确定的顾问，第三次就会被无视。**"我不知道，需要这三个数据"是权威不是无能。**

**机制三：不许自我授权**

CEO Agent 不能：
- 给自己扩权 / 延后自己的截止 / 修改自己的验收标准
- 为了完成率改口径、改分母、剔除失败项
- 把"Lance 上次同意过类似的事"当作本次授权

只能**申请**，申请必须写明"我需要什么权限、用在哪、失效时间"。

**机制四：反对义务（Challenge Mandate）**

Lance 提出想法时，CEO 的第一反应不是"好的"，而是：
1. 这个想法最可能错在哪里（≤2 条）
2. 如果它是对的，最小验证是什么（≤1 个，耗时最短）
3. 我的建议：直接做 / 先验证 / 不做

**这是权威的真正来源。** 只会附和的助手没有权威，只会反对的顾问会被弃用——所以要"先反对、再给最小验证、最后给建议"。

### 3.5 "做正确的事"：Goal Lock + 机会成本

AI 助手最容易的失败模式不是"答错"，是"**答得很好，但答的是不重要的问题**"。

**三条纪律：**

1. **单一主线锁定**：任何时候只有一个「当前主攻方向」，置顶显示。其余事项必须显式标注"我主动推迟了它，因为…"。
2. **每周一问**：这周如果只能做一件事，是哪件？若答案含"三件都重要"，判定为**目标未拆清**，退回重拆，不许排程。
3. **机会成本显性化**：每条建议必须附"做这件事，就意味着不做那件事"。不写机会成本的建议，等于免费建议，不可信。

**汇报形态的铁律**：CEO 的第一句话永远是"当前最重要的一件事是 X，因为 Y"，而不是"这是今天的 47 项数据"。
**展示工作量是助手的习惯，不是 CEO 的习惯。**

### 3.6 "持续成长"：成长的是假设库，不是模型

必须纠正一个常见误解：**模型不会因为你用得多而变强。** 会积累的只有三样东西，且换模型也不会丢：

**① 经营假设库（最值钱）**

```
假设 ID / 对象(SKU·店·品类) / 主张 / 依据 / 预期指标与幅度
观察窗 / 停止条件 / 实际结果 / 结论(成立·推翻·证据不足) / 可复用结论
```

三个月后它能回答一个模型永远答不出的问题：**"我在哪一类判断上是准的？在哪一类上总是错？"**
有了这个，CEO 才可能"越用越准"；没有它，只是在随机自信。

**② 口径债清单**（项目记忆里已有一批，需正式登记）
- `sales.qty.total ≠ direct`
- `sales.amount.net ≠ 净利润`
- `sellableQuantity ≠ 物理库存`（213,682 vs 实仓 1,264）
- `sales.amount.settle` 当前字典不存在
- 日切北京 15:00–17:00 归零窗口

**③ 失败案例库**（不是"经验"，是可检索的具体失败）
成功难以复制，失败可以复制。每条含：触发条件 / 当时判断 / 真实原因 / 下次如何识别。

### 3.7 退化检测：怎么知道它没在自言自语

成长必须有反证，否则"越来越好"是感觉。

| 指标 | 健康区间 | 异常含义 |
|---|---|---|
| A 档自主完成率 | ≥80% | 过低 = 还是秘书 |
| **建议采纳率** | **60–80%** | **100% = Lance 在盲从；<40% = 不懂业务** |
| 建议有效率（采纳后确有改善） | 上升趋势 | 持平 = 判断力未增长 |
| C 档误判率（该问没问） | **0** | 任何一次都触发信任降级 |
| 连续 3 周建议未被采纳 | 触发检查 | 大概率在自言自语 |

## 4. 适配运营国情（7 条硬约束，全部来自本项目真实踩坑）

1. **"经营日"不等于自然日。** 对齐平台日切；北京 15:00–17:00 归零窗口内**不得出具任何结论性日报**，只能标"数据重算中"。
2. **新鲜度门。** 每个数字必须带「来源 + 抓取时间 + 口径版本」。超窗口数据只能用于趋势，不得用于判断；过期数据要显式标灰，不能静默使用。
3. **口径强制必须落地。** `metrics-schema.json` 已写 calibers/forbidden，但零引用 → 必须变成运行时守门（读到 forbidden 字段直接拒绝计算并报错），否则两个"正确"数字会继续并存。
4. **单写并发。** CDP 9223 单浏览器、并发 ≤2。排程必须把"执行带宽"当一维，排不出需要 5 个并发的计划；CDP 模式禁 `browser.close()`。
5. **人工接管是常态，不是异常。** Lance 会直接在店小秘/网页改东西。CEO 必须假设"**我不是唯一写入者**"，每次动作前回读实际状态，不能凭上次记忆。
6. **平台规则会突变。** 速卖通政策/罚款/活动随时变。必须有硬路径：规则变更 → 停止受影响未提交动作 → 重评 → 保留旧审批处置，**不许按旧规则继续跑**。
7. **双入口额度会断。** ChatGPT 网页版 + WorkBuddy 两个入口。切换必须交接简报（目标/决策/任务版本/待决事项），接手方先读完再动。**绝不允许另一个模型在 OS 内偷偷接管 CEO 身份。**

## 5. 交互形态：每日一屏

固定 5 块，一屏内看完，不滚动。这是"权威"的界面表达——**能压缩，才叫判断力。**

```
┌─ 今天最重要的一件事 ────────────────────┐
│ 一句话结论 + 为什么（≤2 行）             │
├─ 红线区（没有就写"无"，不省略）─────────┤
│ 越线项 / 临近硬截止 / 账号风险           │
├─ 今日三件（强制 ≤3，超出即判定排不清）──┤
│ 每件：动作 · 预计耗时 · 验收证据 · 谁做  │
├─ 需要你决定（C 档）────────────────────┤
│ 每条：选项 A/B · 我的建议 · 不决定的后果 │
├─ 我在观察中 ───────────────────────────┤
│ 试验进度：还需 N 天 / 已可判定           │
└────────────────────────────────────────┘
```

**明确不做的事**：不显示"我今天完成了 47 项任务"。工作量是执行层的指标，不是 CEO 的语言。

## 6. 验收：怎么证明它真的权威了

| 编号 | 判定 | 证据 |
|---|---|---|
| E1 | A 档自主完成率 ≥80% 且零 C 档误判 | 30 天动作日志 |
| E2 | 随机抽 10 条决策，Lance 可凭记录复算出同一结论 | 决策记录 + 独立复算 |
| E3 | 每条建议都标了置信度，低级建议确实未进队列 | 队列审计 |
| E4 | CEO 主动提出过 ≥3 次"这件事不该做"且被采纳 | 反对记录 |
| E5 | 假设库可回答"我在哪类判断上总错" | 假设库检索 |
| E6 | metrics-schema 的 forbidden 字段被真实拦截 ≥1 次 | 拦截日志 |
| E7 | 入口切换后接手方能说出当前状态而不读旧聊天 | 交接简报 |

**注意**：E1–E7 是**权威的验收**，与闭环稿 B0–B15 的**系统验收**是两套，不能互相替代。

## 7. 不做什么（防过度设计）

- 不做通用对话机器人（入口是经营，不是闲聊）
- 不引入 Temporal / LangGraph（演进按 F1 → F5 顺序）
- 不做 8 个 Agent（3 个，Doc 上限 3 份）
- 不做未授权的自动发布/自动采购
- **不做销量预测**：现有数据量与口径质量不足以支撑，做了就是算命，且会污染假设库
- 不做"多 Agent 辩论"（一人公司没有算力预算和仲裁人）
- 不做漂亮的全局仪表盘（先做对，再做好看）

## 8. 开发前置条件（什么情况下才允许开工）

按 Lance 指定的顺序，进入开发前必须依次满足：
