# CEO Agent × 一跨 OS 详细闭环方案

版本 v0.1 · 2026-10-26（Asia/Shanghai）· 待审定。

依据：用户已认可的产品定位、目标与活动节奏管理要求，以及对话 × OS 交互方向；承接 [总体业务蓝图](./2026-10-25-ceo-agent-yikua-os-business-blueprint.md)。本轮产出详细闭环与验收设计，不实施产品代码、配置定时任务或执行真实经营动作。具体首店、目标数值、活动日期和授权额度留待使用现有资料初始化。

## 1. 闭环范围与路径选择

首轮场景：**一个店铺的阶段经营目标，结合一次活动或普通经营周期，形成每日任务，跟进执行，并用结果修订次日安排。** 正式发布、付款、改价等不作为首轮必须自动化的条件；能力缺口用可核验人工任务连接，仍必须明确自动化不足。

用户已认可“已有验证能力自动执行、尚未接通能力可人工接管”的方向。对照三种落地路线：

| 路线 | 收益与代价 | 本稿选择 |
|---|---|---|
| 只有每日建议/待办 | 最快，但不负责推进、结果和次日调整 | 不满足本次目标 |
| Agent 决策 + OS 任务/证据 + 自动与人工共同执行 | 可利用已有能力贯通业务，能验证每个交界 | 采用 |
| 首轮把全部业务接成全自动 | 依赖大量未经验证的写入与平台适配 | 留待逐能力成熟后扩展 |

不需要先引入 Temporal、LangGraph 或多个部门 Agent。本稿要求持久检查点、明确重试与待人恢复的行为，具体以现有 Node/SQLite 实现到何处在开发计划里决定；避免仅因技能列出框架就扩大结构。

## 3. 经营闭环表

每一步均保存主体、输入版本、责任、输出及证据。下表的 `G/C/D/P/T/R/E` 为逻辑标识，具体可复用既有存储，不要求创建七套服务。

| 步骤 | 触发/输入 | CEO 经营判断 | OS 行为与记录 | 完成证据与流向 |
|---|---|---|---|---|
| L0 初始化 | 用户目标、现有店铺/商品资料 | 目标是否可量、范围和约束是否足够 | Goal G1、口径与基线引用、缺失清单 | 用户确认版本；缺失只阻塞依赖动作 |
| L1 更新日历与事实 | 到期或事件；平台活动、店铺/商品状态 | 信息是否适用当前店铺、是否过期、是否可比较 | 保存 Calendar Cn、事实引用 E、来源与时间 | 规则、期限、时区、对象映射明确；不完整则调查任务 |
| L2 判断与取舍 | G、C、事实、上次决定、未完成工作 | 做什么、何时做、投入多少、是否值得继续 | Decision Dn：备选、依据、预期、停止条件、复盘时间 | 选择理由可以被人工质疑；无法判断列明缺证 |
| L3 倒排阶段计划 | D、真实活动节点、依赖与容量 | 哪些阶段必须保住，哪些可减范围或放弃 | Plan Pn、里程碑、依赖、资源与冲突 | 每个承诺有可行的前置与容量；不可行明确报告 |
| L4 排定今日任务 | P、到期任务、预计时长、可用资源 | 必做、目标推进、可延后；冲突如何取舍 | 今日计划版本与 Tasks Tn、负责人、期限、验收 | 每个任务可执行/可验收；受阻事项不伪装成已就绪 |
| L5 推进与授权 | 就绪任务、能力和有效授权 | 下一项行动是否仍值得且适用 | 检查前置/版本/执行占用；创建 Run/Attempt，必要时等待审批 | 无资格、无有效授权或能力不成熟则明确停止对应动作 |
| L6 核验执行 | 自动/人工操作回执 | 动作结果是否真正发生、是否匹配目标对象 | 回读、归档 E；完成/失败/待核验 | 完成需证据；结果未知先核对，不自动再提交 |
| L7 日终与次日安排 | 今日实际、未完成原因、变化 | 是否继续、改方案、移期或取消 | Review、明日计划新版本及调整原因 | 今天的事实能解释明天为何变化；保留原承诺 |
| L8 效果复盘 | 观察期到达，基线/结果/其他变化 | 是否改善、证据够不够、是否继续投入 | Review Rn 与后续 Decision | 可为改善/无改善/恶化/证据不足；不强迫得出正面结论 |

周期之间不是每天清空重建：未完成任务沿用原 ID，保留截止与历史；活动规则、目标或输入发生有效变化时修订版本。新问题先判断是否阻塞当前目标，非阻塞列待办，避免无限扩大每日范围。

## 4. 日历、节奏与每日排程细则

### 4.1 日历契约

保存店铺、平台、活动标识、适用商品/资格、准备/报名/预热/活动/收尾阶段、真实期限、平台时区、规则原文引用、核实时间、版本和店铺实际报名状态。未提供的阶段可以不存在，不套用五阶段模板臆造日期。

统一保存绝对时间，界面同时标注平台时区和用户 Asia/Shanghai 时间。出现“PST/PDT”等容易歧义的标签时核对平台真实时区与该日期偏移，不能按文本固定加减小时。规则变更只让受影响的任务和审批进入重评，其他工作继续。

### 4.2 排程方法

1. 锁定用户已确认的目标、预算、活动硬截止和必要保障责任；冲突时提交影响分析，不擅自改写。
2. 先找最迟必须开始的前置链，再检查准备、用户审阅和平台审核可能耗时；临近截止需留核验余量。
3. 按人、浏览器写入会话、店铺对象、生成能力分别计算可用时间。未知预计耗时标区间，禁止把长任务承诺为立即完成。
4. 任务划为：硬期限/保障、目标推进、可延后。分类不是副作用 P0–P6，也不直接决定授权。
5. 对资源竞争，优先选择有较强证据、紧迫且与当前目标相关的任务；保留不做另一任务的理由。没有可信收益估计时不用虚构 ROI 数字排序。
6. 显示今日承诺、暂不承诺及需要用户处理的事项；“必须做”超过容量时明确缺口，而不是排成不可能完成的清单。

最小任务必须包含：关联目标或保障责任、店铺/商品/SKU、具体动作、输入版本、前置依赖、执行者、期限及时间区、预计耗时、授权依据、验收证据、失败处理。粒度停在一次可核验业务动作；不把每次点击都建成经营任务。

### 4.3 滚动推进

- 自动任务回执、审批、用户手动操作和重要外部变化触发重评；输入未改变则复用现有决定。
- 当前对象执行中，新的冲突任务等待；仅“执行占用到期”不能证明旧动作未发生，恢复前须核验结果并阻止过期执行者继续写入。
- 日终区分完成、失败、待人、待数据、结果未知及主动取消；记录影响和次日处理，不一律顺延。
- 错过定时触发后，恢复时合并已错过的检查事件并重新读取现状；过期写入不追赶执行。
- 正常无变化的巡检不刷屏；通知用户有意义的偏差、临近硬期限、确需裁决或执行失败。具体频率在初始化确定，本轮不创建定时任务。

## 5. CEO 的五类经营取舍

本节均为机制推演，不是当前店铺诊断或正式经营规则。阈值须来自用户目标、经核实平台规则或已验证业务策略，不能把旧稿中的 15% 毛利、90 天周转等经验值直接写成生产默认值。

### C1 只有四小时，先补货还是改标题

**示例条件**：今日人工时间四小时；A 商品供给存在临近截止风险，但库存与在途证据尚不完整；B 商品标题优化预计两小时，尚无证据说明标题是当前瓶颈。

先安排二十分钟核对 A 的有效库存/在途和真实截止。风险确认后，预留四十分钟形成供给处置建议或完成人工核对；证据足够且仍有收益依据时安排 B 的两小时内容准备，其余一小时留作审批与异常缓冲。四小时分配为示例，不能自动应用到真实任务。

反例：若 A 的到货已覆盖需求，不继续占用补货处理时间；若 B 有即将截止且证据明确的活动材料要求，重排其优先级。资源有限时输出被推迟事项及影响，不假装两件都能立即完成。

### C2 活动要求降价，是否参加

核对供货价/零售价的区别、实际承担补贴方、成本口径、平台扣费、退款与履约成本、活动资格和供给能力；比较原价经营、降价参加、换商品、退出等选择。

**仅演示算术**：同一计价基础上售价 100、相关单位成本 82，原单位贡献为 18；若全部由商家承担降价至 85、单位成本不变，则单位贡献为 3，贡献率为 3/85≈3.53%。要维持原贡献总额需六倍销量，尚未考虑其他费用与容量。不能用“18%−15%=3%”替代不同分母的计算，也不能假定活动必带来六倍销量。

没有可支持销量、成本和现金约束的证据时，不自行参加；提交条件化建议及缺失信息。即使单位贡献较低，若用户明确选择某种有上限的获客/清货策略，也应在真实授权和观察范围内评估，而非永远拒绝活动。

### C3 连续转化下降：改图、降价还是停止投入

先验证同商品/人群/流量口径及平台延迟，排除断货、不可售、评价变化、价格竞争和活动变化。曝光下降、转化下降和整体件数下降不能互相替代。

有证据指向内容问题时，先做有范围的小试验；有证据指向价格问题时比较贡献和弹性；长期缺少需求、供给不稳定或低于已确认投入底线时才提出停止投入。无证据时先调查，不凭连续三周这个单一条件自动砍品。

试验预先登记主指标、护栏、观察窗和停止条件；避免同时改图、价格、库存后声称是改图起效。无法控制同时变化时降低归因结论强度。

### C4 可能九天后缺货，加急还是接受断档

必须分别确认可用于该商品的可用物理库存、占用关系、到货数量与日期、销售预测及履约模式，不能把平台可售额度当现货，也不能把预计九天后缺货当确定事实。

比较正常到货、加急、减少活动投入、替代供给和接受短期断档。加急成本高三成时，只对相应费用项计算增量，不把所有成本都直接乘 1.3；加急不能在需要日前到达则没有防断档价值。缺贡献、到货或成本证据时先形成调查/审批任务，不自动采购。

### C5 今天什么都不改

输入没有实质变化、动作仍在观察期、样本不足或某事项贡献低于资源成本时，可选择保持现状。记录理由、下一观察点和提前退出条件；不为显得主动而反复改价、改图或创建同一任务。

这五类案例的验收重点是选择能被证据解释、取舍符合目标与约束；不能给“建议写得像总监”打主观高分代替核验。

## 6. 执行、审批、失败与人工接管

### 6.1 两个状态面

业务任务：草稿 → 就绪 → 执行中 → 待核验 → 完成；可分支到受阻、失败、取消。受阻原因包含人、数据、依赖和资源。旧工作流可保留其状态枚举，通过明确映射展示，不为统一显示而丢掉原语义。

经营效果：待观察 → 改善 / 无改善 / 恶化 / 证据不足。外部动作“结果未知”属于执行记录，任务保持待核验；不能当成失败后直接再执行。

### 6.2 动作前检查

服务端检查身份/店铺范围、能力已验证程度、目标与输入版本、资源占用、动作唯一标识、有效授权及预算。聊天和网页使用相同判定。计划批准不等于发布/改价批准；既有明确授权可复用其有效范围，不要求每一步重复确认。

审批绑定对象、动作、参数/内容摘要、版本、有效期及授权范围。退回修改后重新评估适用性；不能因为版本号未变就忽略实际内容变化。能力没有回滚方法时须诚实标“不可逆/需要补偿或人工处置”，不能编造回滚接口。

### 6.3 异常处置表

| 事件 | 自动处理范围 | 等待/升级条件 | 恢复与证据 |
|---|---|---|---|
| 只读采集短时网络失败 | 同一读取请求有界重试 | 次数/时长耗尽、账号失效或口径改变 | 保存失败原因，成功后核对新鲜度 |
| 本地生成质量不合格 | 已授权修复上限内迭代 | 达上限、事实不足、预算耗尽 | 保留候选与 QC，不覆写成合格 |
| 外部提交超时/断线 | 优先只读核对结果 | 无法确认对象或可能重复 | 结果未知→实际回读/人工证据；没有确认前不重建 |
| 平台明确拒绝 | 记录拒绝与受影响对象 | 改参数需新判断或授权 | 修正后创建新尝试，保留原失败 |
| 等用户决定 | 持久等待，计算截止影响 | 影响扩大或临近硬期限 | 同一审批标识恢复；不超时自动放行 |
| 规则过期/活动取消 | 停止受影响尚未提交动作 | 需要更换方案/目标 | 新规则版本、计划差异与旧审批处置 |
| 浏览器或模型不可用 | 保留任务和输入；停止相关写入 | 需要重新登录/切换入口 | 重读上下文并核验实际配置，不静默换模型 |
| 进程/电脑重启 | 恢复任务、检查点与待处理事件 | 旧动作效果不明 | 先核对，再继续；不能从头重跑有副作用流程 |
| 源数据缺失/冲突 | 建立补证任务，独立任务可继续 | 影响后果性判断 | 来源与冲突记录；不默认用旧值/0代替 |
| 任务已过截止 | 阻止过期提交并分析影响 | 减范围、退出或新目标 | 保存原期限，明确未完成责任与新决定 |

重试参数在能力注册时显式定义：只读默认至多两次、生成按已批准流程上限；非幂等外部写入默认不自动重发。此为初稿配置建议，不覆盖现有已授权流程的实际参数，也不把本地有唯一键当平台必然支持幂等。

### 6.4 人工接管与双入口

1. 请求接管后停止新动作；正在执行的动作在安全点结束或进入结果核验。
2. 确认没有仍在写入/结果未知的冲突操作，再交出资源占用。急停阻止后续动作，不能撤销已发生的外部效果。
3. 人工操作留下对象、版本、结果及可核验证据。
4. 恢复前重新读取真实状态、前置与授权；已完成动作不重做。

首期假设同一台机器与共享浏览器资源，采用一个受控写执行入口和上下文版本检查。人工绕过 OS 直接操作平台不能被 OS 锁住；应通过用户通知或回读检测变化，不能承诺所有外部并发都已被防止。

## 8. 数据口径与经营效果验收

### 8.1 本轮发现的字典差异

| 事项 | 核对结果 | 使用规则 |
|---|---|---|
| `sales.qty.total` / `sales.qty.direct` | 当前字典有两种不同口径 | 可分别对同口径前后比；不能混为全店同一销量或直接推算比例 |
| `sales.amount.settle` | 出现在旧勘测/评审表述，但当前字典无此键 | 禁止凭旧文档生成该口径；明确采用实际 gmv/pending/net 中适用字段 |
| `sales.amount.gmv` | 字典为成交金额，发货时间口径 | 不能与下单时间窗口的销量无条件相除 |
| `sales.amount.net` | 平台净收入，不含采购、头程、包装 | 不得宣称是净利润；利润目标需补足成本模型 |
| `conv.rate` | 字典单位为 `%`，脚本使用平台直接值 | 保存单位及原值，跨层核对，不重复乘/除 100 |
| 库存 | 字典/脚本涉及实仓、占用、在途和可售额度；分层脚本存在实仓+占用+在途聚合 | “可售额度”与物理库存分开；占用是否已含在实仓、在途何时可达需业务证据。未核实前该聚合不得直接用于自动采购数量 |

这属于需要验证的明确数据契约，不在本轮改字典或业务计算。旧实测的 474 件、95 件覆盖等数字仅为历史样本，本轮未重新抓取。

### 8.2 三层效果评价

1. 执行层：承诺任务按期且经核验完成比例、重复/错对象操作、恢复与人工处置情况。受阻、失败和主动取消分别报告，不能从分母静默剔除。
2. 经营效率层：同类任务的用户实际投入时间、从发现问题到核验处理的耗时、错过硬截止的事项。先测基线再给目标，不编造节省比例。
3. 经营结果层：同店/同 SKU/同统计口径与窗口下的曝光、转化、销量、可验证贡献或履约指标。按行动选一个主指标和必要护栏，不把所有数据拼成一个分数。

测量有效不等于正向改善。经营结果为负或证据不足时，若记录正确并触发合适的调整，闭环机制可以通过；“系统已带来经营改善”的结论则不能通过。9.5 分愿景另需用户认可的评分体系，不能由本稿单方面兑现。

### 8.3 效果观察记录

每项行动先登记对象、目标、输入版本、动作与实际生效时间、基线窗口、结果窗口、主指标和口径、样本要求/停止条件、成本与风险护栏、其他同时变化和复盘责任。

转化类试验建议先用覆盖完整周内节奏的窗口（通常至少七天），但仍受样本与平台延迟约束；过低样本延长或判证据不足。履约、时效等可用其业务对应窗口。必须保存曝光/访客等适当分母，不能只比较百分比。

没有随机试验或可信对照时，前后比较只能支持相关变化，不能直接归因为 Agent。活动、人群、价格、供给和季节变化必须报告。店铺级流量口径不能直接归因于单 SKU 的改图动作；无 SKU 同口径证据则改用可支持的主指标或判不足。

## 9. 对话与 OS 的交付契约

| 用户交互 | 对话输出 | OS 对应记录 | 检查点 |
|---|---|---|---|

## 11. 运维闭环与开发交付闭环

### 运维闭环

发现异常 → 定位受影响任务/能力/数据 → 停止冲突动作 → 有界恢复或接管 → 回读核验 → 恢复经营。平台状态、生成质量、服务健康和数据新鲜度分别监控；服务在线不代表业务成功，任务失败也不一定是服务离线。

### 开发与额度接续

需求/闭环版本 → 任务认领 → 最小修改 → 检查与独立评审 → 可回滚提交 → 用户验收 → 更新接续记录。

- Codex 与 WorkBuddy 共同开发，同一任务只有一个当前修改者；额度切换转移任务，不复制另一份任务或覆盖整目录。
- 交接记录至少包含：当前目标、分支/基线、已改文件、未提交改动、实跑检查与结果、未解决问题、准确下一步、禁止修改边界。
- 不要求“另一方随时有额度”作为必然条件；备份和接续记录边做边写。
- 实现检查与经营口径检查分开；另一开发者复跑/对账不能只检查实现者生成的同一份预期。
- B15 在产品改动前执行：盘点并审核 WorkBuddy 新资产和忽略脚本，明确哪些可纳入私有仓库并验证恢复。当前旧回滚标签不改写；不纳入账号配置、运行数据或密钥。用户此前已明确授权私有备份，这个方向无需重新从零确认；具体有风险的路径才另核对。
- 现存原目录 server/public/适配器改动仍归 WorkBuddy；Codex 隔离分支可靠性工作单独集成。模型适配问题需入开发计划的生成能力前置，本轮不修改模型目标或默认配置。
