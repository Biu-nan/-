# CEO × 一跨 OS 首条经营闭环：路线图与第一批实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Codex 与 WorkBuddy 共同开发，按用户已确定的额度顺序接续；本文不派发新的并行 Agent。

**Goal:** 为一个店铺的一条经营闭环建立可恢复基线，验证真实入口读取能力，并将后续开发收敛为可验收的纵向交付。

**Architecture:** 外部 CEO 负责判断与调度，OS 保存权威业务状态并提供人工操作。复用现有 Node.js 与 SQLite 载体；先验证现有只读入口，再确定业务命令契约，不把只读状态总账改成第二套任务引擎。

**Tech Stack:** 现有 Node.js ESM、Express、node:sqlite、原生网页、Git 私有仓库；第一批不增加运行框架。

**Spec:** [详细闭环方案](../specs/2026-10-26-ceo-os-operating-loop-design.md)、[自审](../reports/2026-10-26-operating-loop-self-review.md)。

## Global Constraints

- 用户已接受自审建议；当前交付是路线图与第一批计划，非所有产品实现细节均已确认。
- 用户要求先保存现有代码到私有 GitHub，保留回滚机会，再升级。旧回滚标签不改写，不推送公共 origin。
- 不覆盖 WorkBuddy 的六个未提交代码文件；当前认领需双方真实记录，不能代写对方回执。
- 不把官方支持、菜单存在、模拟演示或历史测试算成本次真实集成成功。
- 一个当前经营循环负责人，一个开发任务当前修改者；额度自动检测/接续不作首期前提。
- 不将采购、调价、发布或报名作为第一批验证动作。已有授权仅在其真实范围内适用。
- 不在真实用户数据目录运行合成测试；不启动未经检查的采集/探测脚本。

## Review Focus

1. 备份遗漏被忽略的业务脚本：P0.1 明确盘点，P0.2 在恢复目录逐文件核对。
2. 凭证混入未跟踪资产：P0.1 逐路径分类并检查暂存内容；命中时记录路径，不输出敏感值。
3. 两人同时改动导致快照不一致：P0.2 检查打包前后哈希，变动即重新形成稳定快照。
4. HTTP 成功但数据源失败：P0.3 检查 schema 与各 source 状态，明确“连接通过”与“业务数据可用”分别判定。
5. 待核验被旧七态视图显示为完成：P0.4 必须定义映射及反例，未完成迁移不开放新任务写入。

## 用户可验收的第一版

你提出一个店铺目标后，CEO 能根据同口径事实和已核实期限，给出今日重点与理由；OS 显示同版任务；任务经自动或人工执行后留下可核验证据；日终能解释完成与未完成，并据此调整次日安排。

首条动作链建议选“经营巡检发现一个问题 → 收敛成一项业务任务 → 执行/人工处理 → 核验 → 次日复盘”。具体问题从现有数据选择，不预设当前必然缺货或转化下降。不能只用生成待办作为整条闭环通过标准。

首期只选一个店铺、一个主目标和一类业务动作；同一链路可有多项必要子任务。若没有有效活动，则使用普通经营周期，禁止编造活动。主目标不擅自默认成 GMV；沿用已确认目标，缺失时再请用户确定。

## 整体开发顺序

| 阶段 | 可验收交付 | 前置与出口 |
|---|---|---|
| P0 基线与连接 | 当前资产私有备份与隔离恢复；真实入口只读验证；首条闭环边界和接口设计 | 本文详细计划；产品改动前先过备份门槛 |
| P1 CEO 决策与日计划 | 目标/事实/日历到取舍与日计划的统一契约；五类案例及反例；策略版本与每轮资源上限 | P0 确定首店和事实可用范围；仅生成草稿也必须标明未执行 |
| P2 共享任务与执行核验 | 对话与 OS 读写同一业务任务；版本检查、授权、占用、执行回执与人工接管 | P0 的状态映射、接口设计完成；复用现有任务载体 |
| P3 日终与自动运行 | 未完成事项保留原因并影响次日；实际定时触发、离线恢复、入口接续 | P2 可恢复；无用户消息时测试，不把手动启动算自动 |
| P4 真实试运行 | 固定对象、动作、口径和窗口；执行、效率及经营结果分开评价 | 真实授权与数据可用；允许无改善/证据不足，不伪造达标 |

P1–P4 是交付路线图，尚不是可直接实施的接口级任务。各阶段进入前，基于 P0 的验证结果生成具体文件/方法/测试施工单，避免在未确定连接方式时杜撰全套接口。覆盖闭环设计 §3–§9；P0–P4 合计承接 B0–B15，单独完成 P0 不宣称完整闭环实现。

- [ ] 盘点必要源码及依赖，逐项检查是否含账号、令牌、业务私密数据或机器路径。无法判断的标 review，不能直接纳入。
- [ ] 生成 manifest；include 必须是准确路径和哈希，exclude 说明类型，不以目录整体许可代替审查。
- [ ] 在 Codex 状态中记录 P0.1 的实际认领与文件边界。若需对方暂停当前冲突修改，使用用户已授权沟通渠道；发出与收到分开记。
- [ ] 验证 manifest 可解析、路径唯一、include 文件存在且哈希一致，无 review 项被静默纳入。

验收证据：完整清单及当前代码差异；此任务不运行产品测试、不改变产品行为。

## Task P0.2：私有备份与恢复演练

**Files:**
- Consume: P0.1 manifest。
- Create: `docs/superpowers/reports/2026-10-26-source-baseline-recovery.md`
- Optional Modify: `.gitignore`，仅调整已审查源码的准确白名单，不能开放整个 scripts/。

**Interfaces:** 报告记录私有远程、备份提交 ID、稳定快照的文件清单/哈希、排除项、隔离恢复路径、检查命令和真实结果。不得将代码备份说成业务数据库也已备份。

- [ ] 在已确认不与并行写入冲突的快照中，按 manifest 只纳入 include 项；保留原作者归属，不使用 `git add .`。
- [ ] 复核暂存清单及差异；发现凭证则先移出暂存并修正纳入策略，禁止输出敏感值。
- [ ] 建立新的备份提交/分支；不改旧标签，不重置原工作目录，不覆盖 WorkBuddy 改动。
- [ ] 向已授权私有仓库推送并回读提交；认证或网络失败如实记录，不声称远程已备份。
- [ ] 在独立恢复目录恢复该提交，逐项核对哈希与关键依赖。重复检查源快照稳定性，若发生并行变更则注明排除或重新取快照。
- [ ] 对恢复源码执行适用的 `node --check <文件路径>`。在隔离 `USER_DATA_DIR`、TEMP/TMP 下运行已核对可安全执行的必要检查；命令与结果写入报告。

通过标准：远程提交可回读、恢复副本与纳入清单一致、必要源码解析成功；不能仅以本地 commit 成功代替 B15。现有全量测试有历史失败，若运行必须按失败集合对照，不能称全绿。

## Task P0.3：验证一个真实经营入口的只读连接

**Files:**
- Read: `dist/src/server.js`、`dist/src/system-state.js`、实际宿主连接配置（不抄录密钥）。
- Create: `docs/superpowers/reports/2026-10-26-ceo-entry-connectivity.md`

**Interfaces:** 调用现有 `GET /api/system/state`，响应须包含 `schema: "system-state/v1"`。报告按入口记录 host/product、传输方式、时间、schema、sources 健康状态、工具可用性、错误与证据位置；入口只读、模拟写入、定时触发三项分别标 verified/unverified/failed。

- [ ] 确认用户实际准备使用的 Work/WorkBuddy 入口及已存在连接方式；不把本 Codex 工程会话的访问能力等同于目标经营入口。
- [ ] 识别已有 OS 监听地址与服务状态；不为探测而重启生产服务，也不把本机端口公开到公网。
- [ ] 从目标入口调用只读状态接口，记录脱敏结果。若该入口暂无法接入，只证明现有可用入口，另一个明确记未验证。
- [ ] 核对 schema、来源错误及时间；分别判断连接成功、数据可用和数据足够支持经营，不将 HTTP 200 作为三者均通过。
- [ ] 验证失败时输出最小连接缺口与下一项接口工作；不通过试写真实业务来证明连接。

通过标准：至少一个目标经营入口实际取回可识别 OS 状态，并准确描述不可用来源。此任务不包含模拟任务写入或自动定时验证；这些在 P2/P3 完成。
