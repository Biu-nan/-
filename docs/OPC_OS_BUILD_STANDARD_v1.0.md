> **① 什么是 OPC 公司 → ② OS 核心解决什么问题 → ③ 什么叫"好" → ④ 建成什么样算建成。**

## 0. 一句话

> **好 OS 的标准不是"能做多少事"，而是"能不能在你不在的时候，生意还在按你的判断往前走，且不出事、说得清、记得住"。**

---

## 1. 先定义 OPC 公司

不定义这个，标准一定是错的——因为你会照搬大公司的 OS 标准。

### 1.1 OPC 的五个结构性事实

| 事实 | 含义 | 推出的约束 |
|---|---|---|
| **F1 只有一个决策者** | 没有分工，没有中层，所有判断最终汇到一个人 | 决策带宽 = 公司规模上限 |
| **F2 没有组织冗余** | 大公司犯错有缓冲层，OPC 犯错直接到结果 | 不可逆错误的代价极高 |
| **F3 注意力不可扩容** | 钱可以加，人可以外包，注意力不行 | 时间是最贵的资源 |
| **F4 所有职能一人兼** | 商品/流量/采购/财务/客服全是同一个人 | 必须按"节拍"而非"职能"组织 |
| **F5 后果 100% 自担** | 没有董事会分摊、没有部门背锅 | 生存优先于增长 |

### 1.2 由此推出的第一性原理

**OPC OS 的第一性原理不是效率，是生存。**

| | 大公司 OS | OPC OS |
|---|---|---|
| 优化目标 | 增长（规模效应） | 不出局，再谈增长 |
| 失败模式 | 增长停滞 | 一次不可逆错误 |
| 加人能否解决 | 能 | 不能 |
| 瓶颈 | 资本 / 市场 | **决策带宽** |
| 冗余 | 有（可容错） | 无（必须零致命错） |

**这条直接决定了三件事：**

1. **C 档授权必须极窄**。大公司可以给区域经理很大权限，因为有审计和兜底；OPC 没有兜底，一次毁店就结束了。
2. **"少做"比"多做"更值钱**。产出可以慢慢来，出局是一次性的。
3. **OS 的价值上限 = 它能把决策带宽扩到多大**。这是唯一值得追求的规模指标。

## 2. 核心解决什么问题

### 2.1 三层问题（越往下越接近本质）

**表层（用户会这么描述）**
> "我太忙，事情太多，看不清楚店里到底在发生什么。"

**中层（真实痛点）**
> "我做决策缺依据。依据不可信（2302 还是 64？），可信的依据要花两小时去找，找到时窗口已经过了。"

**本质（真问题）**
> **一个人的判断力被"操作"吃掉了。**

### 2.2 本质定义

> **OPC AI OS = 把一个人从"经营的操作者"，变成"经营的裁决者"。**

拆开是三件事在时间上解耦：

| 环节 | 传统一人电商 | 有 OS 之后 |
|---|---|---|
| **看见** | 要主动去翻、去问、去抓 | 常驻自动，异常才叫人 |
| **判断** | 看见的同一时刻就要判断 | 异步化，人只在关键节点介入 |
| **执行** | 判断完自己动手 | 系统跑，人只看回执 |

**可量化表述：提升单位时间内的高质量决策数。**
一个团队的价值不是"人多"，是"一天能做出 50 个高质量决策"。好的 OPC OS 让一个人接近这个数。

### 2.3 明确"不解决什么"（同样重要）

| 不是 | 为什么 |
|---|---|
| 不是"让你少干活" | 那是效率工具。OS 可能让你更忙——忙在判断上，不忙在操作上 |
| 不是"自动化一切" | 高后果动作必须留人。全自动 = 全风险 |
| 不是"让你变聪明" | 它不提供商业智慧，只提供可复算的依据 |
| 不是"漂亮的仪表盘" | 看得好看 ≠ 判断得对。先做对，再做好看 |
| 不是"更多 Agent" | Agent 数量是成本项，不是能力项 |
| 不是"销量预测" | 现有数据质量不足以支撑，做了就是算命 |

## 3. 什么叫"好"：三条本质标准

一个人要把生意托付给一套系统，只需要三个条件。**缺一条，托付就不成立。**

### 标准一：可信（Trustworthy）
> **它说的数字是真的，且只有一个版本。**

- 任何一个数字，能从原始数据独立复算出同一结果
- 同一个问题，对话入口和网页入口给出同一个答案
- 数据过期、口径不明时，主动标灰说"这个不能用来判断"

**不合格的典型表现**：同一个店同期，销售管理说 2302 件，商品分析说 64 件，两个都"正确"。

### 标准二：可控（Controllable）
> **它知道自己不能做什么，且停得住。**

- C 档动作零漏报（该问的一定问）
- 结果未知时先回读核实，**绝不重跑有副作用的流程**
- 平台规则变了能停机重评，不按旧规则硬跑
- 人随时能接管，接管后系统不假装自己还在控制

**不合格的典型表现**：改价改错了没人知道；提交超时后自动重试，导致下两次单。

### 标准三：可成长（Compoundable）
> **它记得住，所以越用越准；而且这件事不依赖模型。**

- 三个月后能回答："我在哪一类判断上总是错？"
- 换模型、换入口，积累的东西还在
- 能主动说"这件事我以前判断错过，原因是…"

**不合格的典型表现**：每次对话都要重新解释一遍业务；同一个坑踩第四次。

> **注意**：可成长 ≠ 模型变强。模型不会因为你用得多而变强。会积累的只有假设库、口径债、失败案例——这些是**你的资产**，不是模型的。

## 4. 建成标准：三个可判定的测试

不用功能清单验收，用**测试**验收。过了就是建成，过不了就是没建成，不靠感觉。

### 测试一：托付测试（最重要）

> **连续 3 天不主动看系统，回来时：**
> 1. 系统在 1 屏内说清这 3 天发生了什么
> 2. 说清它替你做了哪些决定，各自的依据
> 3. 说清哪些它没敢做，在等你裁决
> 4. **零不可逆错误**

**这一条过了，OS 才叫建成。** 前三条测"可信"，第四条测"可控"。

### 测试二：复算测试（口径）

> 随机挑 10 个展示出来的数字，从原始数据独立复算，必须全部一致。

**当前状态：大概率不过。** `metrics-schema.json` 已定义 forbidden 字段但代码零引用。

### 测试三：接手测试（解耦）

> 换一个完全不了解情况的人（或一个全新模型），只读交接简报，能否说出：当前目标、正在进行的事、待决事项、下一步。

**这条测的是"系统是否独立于 Lance 的记忆"。** 过不了，说明知识还在人脑里，不在 OS 里。

---

## 5. 七个能力要素（可勾选清单）

三个测试是总验收，七要素是**逐项自查**。每项都有 pass/fail，不打分。

| # | 要素 | 判定方法 | 不合格的典型表现 |
|---|---|---|---|
| 1 | **单一事实源** | 同一问题两入口同答案 | 2302 vs 64 |
| 2 | **口径可强制** | forbidden 字段被真实拦截 ≥1 次 | 字典写了、零引用 |
| 3 | **状态可回读** | 动作后回读一致 | 结果未知就重跑 |
| 4 | **判断可复算** | 同输入复算同结论 | 只有结论没有依据 |
| 5 | **边界可执行** | C 档 7 条零漏 | 该问没问 |
| 6 | **记忆可检索** | 能回答"哪类判断总错" | 每次从零解释业务 |
| 7 | **人可离开** | 3 天不看不出事 | 离开一天就乱 |

**要素 1–3 属于"可信"，4–5 属于"可控"，6–7 属于"可成长"。**
**任何一条不合格，都不能宣称 OS 建成。**

## 6. OS 本身的三条"好"的形状特征

前面是标准，这里是**好 OS 长什么样**——三条反直觉的形状。

### 6.1 好 OS 的核心能力是"减法"，不是"加法"

OPC 的约束是注意力。所以：

> **一个能告诉你"这周只做这 3 件，其余 47 件我替你推掉了，理由如下"的系统，好过一个能做 50 件事的系统，10 倍。**

市面上所有 ERP / BI 都是加法工具——它们帮你看见更多、做更多。**没有一个帮你放弃。**
这恰恰是 OPC 最缺的能力。**这也是这类产品真正的差异化所在。**

### 6.2 好 OS 主动说"不"

- 排不下时明确说"排不下"，不排出假清单
- 证据不足时明确说"不知道"，不给看似专业的建议
- 建议会标注置信度，推测级不进队列
- 会主动提出"这件事不该做"

**一个从不拒绝的系统，等于没有判断力。**

### 6.3 好 OS 的第一句永远是结论，不是数据

- 先说"今天最重要的一件事是 X，因为 Y"
- 再说"红线区：无"
- 最后才是细节

**展示工作量是助手的习惯，不是经营者的语言。**

## 7. OS 成熟度分级（自身评估用）

| 级 | 名称 | 判定 | 一跨 OS 当前 |
|---|---|---|---|
| **L0** | 记录级 | 能存、能查、能跑通单个流程 | ✅ 已过（254 路由，上新链路 L3） |
| **L1** | 可见级 | 口径唯一，一屏看清经营现状 | ❌ 未过（无单一事实源，字典零引用） |
| **L2** | 判断级 | 能给出可复算、可质疑的建议 | ❌ 未过（无决策记录） |
| **L3** | 托付级 | 通过托付测试，3 天自主运行 | ❌ 未过 |
| **L4** | 进化级 | 假设库驱动，越用越准，可证明 | ❌ 未过 |

> **当前定位：L0 与 L1 之间。**
> 这是一个诚实的位置。它的意义是：**不要再讨论"要不要加 Agent"，先过 L1。**
> L1 的唯一门槛就是复算测试——而它的技术前提是把已经写好的 `metrics-schema.json` 变成运行时守门。

## 8. 什么不算"建成了"（反面清单）

以下任何一条成立，都不能宣称建成，无论功能多少：

1. 同一个指标两个入口两个答案
2. 做过的决定查不到依据
3. 关掉对话窗口，系统就停止工作
4. 需要 Lance 在场才能判断"现在该做什么"
5. 换一个模型，之前积累的经验全部消失
6. 出现过一次"该问没问"的高后果动作
7. 说不清"这周为什么只做这三件事"
8. 只能回答"发生了什么"，回答不了"所以我该怎么办"
9. 数据过期了还在被用来做判断，且没有提示
10. 系统告诉你的都是你本来就知道的

> 第 10 条最阴险：**如果 OS 说的每句话你都知道，那它只是把你的认知打印了一遍，价值为零。**
