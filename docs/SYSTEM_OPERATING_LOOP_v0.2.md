# 系统运营闭环 v0.2 · 借鉴行业标杆重构框架

> 2026-10-25 · 在 v0.1 盘点基础上，引入跨境电商 ERP / BI 行业模型
> 决策依据：D1 = 后台抓取（店小秘 + 稳卖浏览器）；D2 = 混合驱动（节拍 + 阈值）

---

## 一、行业对标：一条被反复验证的分层铁律

查了三家主流 ERP（领星 / 马帮 / 店小秘）与跨境 BI 的架构说明，**同一条结论在不同来源重复出现**：

> **「ERP 管执行，BI 管决策，这才是完整的运营闭环。」**
>
> 原因不是厂商能力问题，是**架构基因**：ERP 底层是事务型数据库（OLTP），为快速处理订单、库存记录而优化，**不适合海量数据的多维聚合与复杂计算**。所以 ERP 的跨平台利润永远算不准——这是品类缺陷，不是实施问题。

**这条铁律直接给你的系统定位：**

| 层 | 职责 | 一跨而境现状 |
|---|---|---|
| **执行层（ERP）** | 刊登、上下架、改价、库存、订单流转 | ✅ **已经建了，而且做得很深**（14 域 / 140 路由） |
| **决策层（BI）** | 利润核算、五层诊断、生命周期判定、动作建议 | ❌ **基本空白**（today-dashboard 只有 7 个任务计数） |
| **数据层（采集）** | 从平台/后台抓原始事实 | ❌ **空白**（performanceSnapshot 纯手工录入） |

**所以你不是"缺一个对话入口"，你是缺了整个决策层。** 对话框只是它的嘴。

参考标杆分工：
- **领星**：学它的「ASIN 级利润核算」——每个 SKU 的收入、广告、退货、平台费自动归集，出单品 P&L。
- **数跨境 BI**：学它的「五层诊断模型」（下面第二节），这是目前看到最可直接落地的诊断框架。
- **马帮**：学它的「供应链全链路」，但你现在是 Choice 半托管，这一层暂不需要。
- **店小秘**：这是你已有的执行底座，不需要再学。

## 二、决策层的核心：五层诊断模型（行业已验证）

复盘时**按顺序往下走**，不要五层一起看——上层的异常往往是下层问题的表现。

| 层 | 核心指标 | 异常时的追问 |
|---|---|---|
| **1 利润层** | 单品净利率、毛利率、TACOS、退款损失率 | 利润下滑是价格、成本，还是结构问题？ |
| **2 流量层** | 曝光量、点击率、搜索词集中度、**自然流量占比** | 流量是变少了、变贵了，还是变杂了？ |
| **3 转化层** | 转化率、加购率、评论数与评分、**Listing 完成度** | 下滑发生在哪个入口？是否与评论变化同步？ |
| **4 履约层** | 库存周转天数、动销率、库龄结构、缺货率 | 是缺货导致断流，还是滞销占用资金？ |
| **5 现金流层** | 资金占用、回款周期、铺货资金效率 | 账面利润与现金回流的差距来自哪？ |

**判断顺序反直觉但重要：先看利润结构，再看流量结构。** 因为流量优化的方向必须由利润结构决定，不能反过来。

## 三、指标体系：三层，每条带警戒线

| 层级 | 指标 | 周期 | 警戒线（可直接用） |
|---|---|---|---|
| **结果层** | SKU 毛利率（含头程与退货） | 周 | **< 15% 进排查** |
| | 库存周转天数 | 周 | **> 90 天启动清货** |
| | 动销率 | 月 | **< 40% 需砍品** |
| **过程层** | Listing 转化率 | 周 | **环比下滑 > 20% 排查** |
| | 广告占利比（广告费/毛利） | 周 | **> 0.45 调结构** |
| | 退货率 | 周 | **> 8% 拆解原因** |
| | 履约时效 | 周 | **> 12 天预警** |
| **健康层** | 账号绩效与合规 | 日 | 触及平台阈值即升级 |
| | 供应商交付准时率 | 月 | < 90% 谈备选 |
| | 核心 SKU 断货风险 | 日 | 见库存周转 |

**硬规则：过程指标不超过 12 项。** 超过之后每次复盘都变成"每个都没看透"。宁可少，但每一项都必须有人能说出它上周为什么动。

**对单人 + AI 的极简版**（这条最适合你现阶段的规模）：
> 只盯三个指标 —— 核心 SKU 的 7 天移动平均销量、核心渠道转化率、库存周转天数。每周一小时复盘。

## 四、商品生命周期：四阶段 × 每阶段只盯 2–3 指标

这是「商品完整周期」的骨架。**阶段识别不能只看销量绝对值**（否则会把刚上架的新品误判成衰退品）。

### 识别方法（三维交叉，周颗粒度，剔除大促周）

```
趋势：近 8 周环比增速 + 移动平均斜率，连续 3 周为正且增速 > 15% → 上升通道
效率：毛利率是否稳定或走高（排除靠降价冲量的假增长）
质量：复购率 / 连带率（判断需求是真实还是促销拉动）
```

### 阶段 → 指标 → 动作（可直接落成工单模板）

| 阶段 | 时间锚 | 只盯这 2–3 个 | 该做的动作 | 最容易犯的错 |
|---|---|---|---|---|
| **导入期** | 上架 0–30 天 | 转化率、加购率、点击率 | 小流量测试、优化主图标题、破零积累评价 | **过早放量**：数据没验证就猛投，排名反而更差 |
| **成长期** | 30–90 天 | 销量增速、库存周转天数 | 按周滚动补货、抢关键词自然位 | 断货或压货 |
| **成熟期** | 90–180 天 | 毛利率、复购率 | 提客单、做组合装、延伸 SKU | **拼价格**（该做的是提客单） |
| **衰退期** | 180 天+ 或连续下滑 | 清仓速度、连带率 | 阶梯降价（10% 一档观察一周）、捆绑清尾货 | 情感因素硬撑 |

**滞销定义必须先写死**（否则口径一变结果差一倍）：例如「连续 4 周销量低于类目均值」或「库存周转 > 90 天」。

## 五、架构：双环 + 一条数据动脉

```
                    ┌──────────────────────────────┐
                    │     对话入口（运营总监）        │
                    └───────────────┬──────────────┘
                                    │
              ┌─────────────────────┴─────────────────────┐
              │                                           │
    ┌─────────▼──────────┐                    ┌───────────▼──────────┐
    │  A · 决策环（BI）   │                    │  B · 执行环（ERP）    │
    │  五层诊断           │   ── 工单 ──▶      │  选品 建档 文案 主图  │
    │  生命周期判定       │   （你批准）        │  上架 改价 清仓 暂停  │
    │  动作建议 / 告警    │   ◀── 回执 ──      │  ← 已有 140 路由      │
    └─────────▲──────────┘                    └───────────▲──────────┘
              │                                           │
              │              ┌────────────────────────────┴───┐
              └──────────────┤  C · 数据动脉（D1 后台抓取）     │
                             │  稳卖浏览器 → 销量/流量/结算     │
                             │  店小秘     → 商品/库存/刊登状态  │
                             └────────────────────────────────┘
```

**三条不可违背的流向规则：**

1. **决策环不直接执行**，只产出「工单」；执行环不自己判断该做什么，只执行工单。违反就是双大脑。
2. **工单必须过你这一关**（P3+ 动作）。这就是你的 `L2 · O0` 定位——自主性是"工作流级"，监督是"每次后果性动作人批"。
3. **数据动脉只进事实，不进结论**（见第六节）。

## 六、D1 · 数据动脉设计（后台抓取）

### 采集源与分工

| 源 | 取什么 | 已知可用性 |
|---|---|---|
| **稳卖浏览器**（多店铺） | 销量、曝光/点击、转化、结算金额、退款、评价 | 已有店铺 API 接入经验（UNKNOWN：字段覆盖度需实测） |
| **店小秘** | 商品清单、库存、刊登状态、审核状态 | 已有 CDP 9223 + `dianxiaomi-adapter`，复用成本最低 |
| **速卖通 Choice 后台** | 结算明细、平台扣费 | **UNKNOWN** —— 半托管模式下能否看到分项费用，必须登录核验 |

### 两条硬规矩

**规矩 1：原始事实落库，指标永远可重算。**
不要直接把算好的"毛利率"当唯一真相存下来——口径一变（比如头程分摊方式改了）历史全废。正确做法是落原始事实表，指标按当前口径实时算。

```jsonc
// data/metrics/facts/YYYY-MM-DD.jsonl —— 一行一条，只追加不改
{ "skuId": "...", "storeId": "...", "date": "2026-10-25",
  "raw": { "soldUnits": 12, "gmv": 356.4, "settleAmount": 301.2,
           "adSpend": 18.0, "refundAmount": 12.5,
           "impressions": 4210, "clicks": 168, "visits": 402 },
  "source": "wenmai", "capturedAt": "..." }
```

**规矩 2：抓取必须幂等 + 可补历史。**
按 `(skuId, storeId, date)` 唯一键 upsert。同一天重复抓 → 覆盖不翻倍。断了一天 → 能补。否则一个网络抖动就污染整个趋势线。

### 与现有代码的关系

- `createPerformanceSnapshot()` 不废弃，改造成「**手工补录通道**」：自动抓取拿不到的字段（如头程成本、包装成本）由它兜底。
- 新增 `metrics-service`：抓取 → 归一 → 落事实表 → 按口径算指标快照。
- `today-dashboard` 改造：从"7 个任务计数"升级为"任务计数 + 经营指标摘要"。

## 七、D2 · 混合驱动设计（节拍 + 阈值）

两种触发器，**同构**——都产出工单，都进同一个队列。

### 4.1 节拍器（Calendar Trigger）

| 节拍 | 时间 | 扫什么 | 产出 |
|---|---|---|---|
| **日扫** | 每天固定时刻 | 断货风险、异常单量波动、失败任务 | 紧急工单（≤3 条，多了等于没有） |
| **周复盘** | 每周固定 | 过程层指标 + 生命周期阶段重判 | 复盘报告 + 动作工单 |
| **月盘点** | 每月 | 动销率、砍品清单、补货计划 | 结构性决策工单 |

### 4.2 阈值器（Event Trigger）

```
触发条件                                    → 工单类型
SKU 毛利率 < 15%                            → 【利润排查】价格/成本/结构三选一
库存周转 > 90 天                            → 【清货】阶梯降价 or 捆绑
动销率 < 40%（月）                          → 【砍品评估】
Listing 转化率环比 ↓ > 20%                  → 【Listing 诊断】流量入口定位
广告占利比 > 0.45                           → 【投放结构】
退货率 > 8%                                 → 【原因拆解】客服+品控
商品进入衰退期判定                          → 【退出 SOP】
```

### 4.3 去重与抑制（这一层不做，系统会变成告警地狱）

- 同 SKU 同类型工单 **7 天内不重复生成**（已有未关闭工单 → 累加提醒次数，不新建）
- 工单带 `priority`：P0 断货/合规 > P1 利润异常 > P2 结构优化
- **每日工单上限**：超过 N 条只推 top-N，其余进 backlog

这里直接复用现有骨架：`operationProfiles.next_review_at`（节拍锚）+ `operations/tasks`（工单）+ `daily-waiting-items`（今日队列）+ `agent_summary`（复盘记录）。**骨架已经在，缺的是生成器。**

## 八、运维闭环（系统自身健康）

这是你说的"运维闭环"，与运营闭环分开但同构——都是「发现异常 → 定位 → 处置 → 验证」。

| 监控项 | 判据 | 自动处置 |
|---|---|---|
| 批量任务假死 | `running=true` 但无活跃 item 且 > 90s 无心跳 | 已有自愈（`normalizeXxx`），保留 |
| Server 重启丢态 | `!jobId` 但有磁盘状态 | 已有 `recoverBatchListingState`，保留 |
| Chrome/CDP 掉线 | `/json/version` 探活失败 | 重连 → 仍失败则降级为"需人工登录" |
| 状态漂移 | 内存态 vs 磁盘态不一致 | 以磁盘为准（磁盘是唯一真相） |
| 数据动脉断流 | 今日抓取 0 条 或 抓取耗时 > 阈值 | 告警，且**明确标注"数据未更新"而不是显示旧数据** |

**最后一条最重要**：数据没抓到就显示"数据未更新"，绝不用昨天的数当今天的——这正是你之前吃过的亏（FAILED 显示成"待开始 0%"）的同类问题。

## 十、Operating Point 与权限分级

按 `agent-builder` 标准声明（不声明就不许实现）：

```
自主性：L2（Workflow）为主 —— 诊断/判定走确定性流水线，LLM 只在诊断归因时介入
        局部 L3 —— 复盘归因时由 LLM 分解"利润为什么跌"（路径不可枚举）
监督：  O0 —— 每个 P3+ 动作人批（符合你"发布必须我点"的一贯要求）
架构：  单 agent（运营是 depth-first：一个店铺/一个商品的连续上下文）
        不用多 agent —— 那是 breadth-first 研究任务才需要的
```

权限分级（代码强制，不写在 prompt 里）：

| 级别 | 动作 | 策略 |
|---|---|---|
| **P0** | 读状态、算指标、出诊断 | 静默执行 |
| **P1** | 生成报告、出工单建议 | 静默执行，进队列 |
| **P2** | 建档、出草稿、改本地数据 | 执行并播报 |
| **P3** | 改价、改 Listing、上传 | **需你确认** |
| **P4** | 提交上架、发布 | **需你确认** |
| **P5** | 批量操作（>5 个 SKU） | **需你确认 + 二次确认** |
| **P6** | 删除、清空、回滚 | **每次单独确认** |

## 十一、落地顺序

| 阶段 | 内容 | 前置 | 风险 |
|---|---|---|---|
| **P0** | L1 总账 `GET /api/system/state` | 无 | 只读，零 |
| **P1** | **D1 探路**：登录店小秘 + 稳卖，实测能抓到哪些字段 | 需要你配合登录 | 只读抓取，低 |
| **P2** | 事实表 + metrics-service（动销率/周转/毛利三指标先跑通） | P1 | 低 |
| **P3** | 阈值器 + 工单生成（先只做 3 条最有用的规则） | P2 | 低 |
| **P4** | 执行环合体（v0.1 的 ②+③ 方案） | P0 | 中 |
| **P5** | 节拍器（日扫/周复盘/月盘点） | P3+P4 | 低 |
| **P6** | 复盘沉淀 + 生命周期判定引擎 | P5 | 中 |

**为什么 P1 是"探路"而不是直接开发**：Choice 半托管后台到底能看到哪些结算字段，现在全是 UNKNOWN。不先实测就写抓取代码，等于闭着眼睛建管道。
