# 回写规则建议（L7 学习进化层）

> 日期：2026-11-10｜状态：**建议草案，待 Human 批准**
> 回答的问题：一份报告写完之后，什么条件下它里面的结论**必须**变成 `prompts/` 或 `contract.md` 的修改？

---

## 0. 先说结论

**我建议的不是"事后挖报告"，而是把回写责任前移到写报告的那一刻。**

理由：现在有 49 份报告，靠事后回忆去挖"哪条该回写"，等于没规则。真正可执行的做法是——**报告模板里强制留一段「可回写结论」表，写报告的人当场就想清楚**。空着也可以，但必须显式写「无」。

配套三条硬规则：

1. **只有三类情况触发回写**，其余一律不触发（防止文档被噪音淹没）
2. **每条回写必须带证据位置**，无证据不许提交
3. **生成变更建议，不直接改文件**，人批了才落盘

---

## 1. 三类触发条件

### T1 · 口径修正（强制，最高优先）

**触发**：报告中出现同一指标在两个来源、两个页面或两个时间窗得到不同数值，差异 > 5%，且两边都能给出可回读证据。

**为什么强制**：口径错误会污染所有下游计算，而且会重复犯——同样的坑踩第二次才发现就太晚了。

**落到哪**：`config/metrics-schema.json` 的 `forbidden` 或 `warning` 字段 + 对应 `prompts/` 的口径说明段。

**已有真实案例（可直接抽取）**：

| 案例 | 证据位置 | 应回写内容 |
|---|---|---|
| 销售管理支付件数含货通、商品分析不含，同店同期 2302 vs 64 | `CEO agent/CEO_Diagnosis_1005011985916829_20261109.md` 第 165 行 | `forbidden` 已有此条，需补"具体页面级差异实例" |
| 用仓库出库数推算基板渗透率得 63%，按支付件数口径只有 14.1% | 同上，第 165 行 | 应加进 `forbidden`：**"禁止用仓库出库数代替订单/件数推算占比"** |
| 平台日界 PST 与北京业务日界不同，日切 15:00–17:00 归零 | `config/metrics-schema.json` timezone 段 | 已有，需补"归零时段跳过不写库"的采集器约束 |

→ **这一条现在就能抽出至少 1 条新 forbidden。**

### T2 · 阈值修正（强制）

**触发**：报告中某个判定阈值被实测数据推翻 **≥2 次**（同一阈值、同一方向）。

**为什么是 2 次而不是 1 次**：单次异常是噪声，换规则会误伤。两次同向才叫规律。

**落到哪**：对应 `prompts/` 里的阈值 + 在报告里记录「原值 → 新值 → 依据」。

**已有真实案例**：诊断报告里「转化率 1.5–2.5%（类目基准）」这个阈值，单品实测 5.93%→5.85%→6.31%，是这个基准的 2.5 倍。**目前只 1 次，按规则暂不改**，但应记为「待观察：1/2」。这个"待观察计数"本身就该进 `prompts` 的阈值旁边。

### T3 · 经验沉淀（需人批）

**触发**（满足任一）：
- **(a) 失效**：某做法被有回读证据地证实无效
- **(b) 可复现**：某做法 **≥2 次**产生可验证的正面结果

**落到哪**：`prompts/` 的案例段，或 `contract.md` 的 `known-failures` / `known-good` 段。

**已有真实案例**：

| 案例 | 类型 | 应回写内容 |
|---|---|---|
| "大号 -77.78% 在崩、85 件够用"是单日环比误判，应看近 30 天与平台预测 | (a) 失效 | `prompts/` 诊断方法段：**禁止用单日环比判定趋势，必须同时给近 30 天与平台预测** |
| 多件装采购成本线性但供货价只给 2.00×，每只让 32% 单价 | (b) 可复现 | 待验证第 2 次后写入选品定价案例 |

→ **这一条现在就能抽出 1 条方法层教训。**

---

## 2. 明确不触发回写的四类

| 不触发 | 理由 |
|---|---|
| 单次异常、单次数据缺失 | 噪声，不是规律 |
| 无实证的推断（报告里标 `INFERENCE` 的段） | 推断不能变成规则 |
| 已被现有文档覆盖的内容 | 重复回写会让文档膨胀 |
| 与具体店铺绑定的易变状态（当前库存缺口、本周排名） | 这类属于事实，不属于方法 |

---

## 3. 落地机制（三件具体的东西）

### 3.1 报告模板强制留段

每份报告末尾必须有这一段，没有就写「无」，但**不许不写**：

```markdown
## 可回写结论

| 类型 | 目标文件 | 目标段落 | 原内容 | 建议新内容 | 依据（本报告证据位置） |
|---|---|---|---|---|---|
| T1 | config/metrics-schema.json | forbidden[5] | — | 禁止用仓库出库数代替订单数推算占比 | §2 第 165 行，出库 2154 只 vs 支付 778 件 |
```

六列都是必填。`依据` 一列必须指向本报告内的可定位位置，不是"参考行业经验"这种话。

### 3.2 抽取器 → 变更建议

```
报告（含可回写表）
  → 抽取器解析表格
  → 生成变更建议 data/writeback-proposals/{YYYY-MM-DD}/{seq}.json
  → 必含字段：type / targetFile / targetSection / oldText / newText / evidenceRef / sourceReport
```

**闸门：`evidenceRef` 为空或指向报告外部的，直接拒收。**

### 3.3 人批 → 落盘 → 记账

```
变更建议 → Human 逐条批准（可批 / 驳回 / 改后再批）
  → 批准项落盘
  → 记入 docs/CHANGELOG-writeback.md（时间、类型、目标、diff、批准人）
  → 重跑相关测试，失败则回滚
```

**不允许自动落盘。** 文档是这套系统的资产本体，自动改会让资产失真——而且失真了没人发现，因为没人看。

---

## 4. 验收标准

| # | 标准 | 怎么验 |
|---|---|---|
| 1 | 现有 49 份报告能抽出 ≥1 条有效回写建议 | 跑抽取器，看输出条数 |
| 2 | 每条建议有 evidenceRef | 逐条检查非空 |
| 3 | 无 evidenceRef 的建议被拒收 | 构造一条空的，必须报错 |
| 4 | 落盘后 prompts 文件 hash 变化可追溯 | 比对修改前后 sha256 + CHANGELOG |
| 5 | 回写后相关测试仍通过 | 跑对应测试文件 |

---

## 5. 为什么不做自动化

两条理由，都不是技术原因：

1. **项目红线**：文档修改必须人批，不自作主张。
2. **资产失真无人发现**：prompts 和 contract 是这套系统唯一不可替代的东西。如果自动改，改错了没有第二个人知道——因为唯一的读者就是下一次的 Agent，它会照着错的规则跑，而且跑得很有信心。**这种错误比代码 bug 危险得多，代码会报错，文档不会。**

---

## 6. 我的建议：分两步走

**第一步（今天就能做）**：只做 T1，只做「抽取 + 变更建议 + 人批」，不碰 T2/T3。
理由：T1 有硬证据（5% 差异、双向可回读），最容易判定，也最该先修。先跑通一小段，证明机制可用。

**第二步（跑通后再做）**：加 T2 的「待观察计数」，再放开 T3。

不建议一次把三类都上——**规则太复杂就等于没有规则**，最后没人填那张表。
