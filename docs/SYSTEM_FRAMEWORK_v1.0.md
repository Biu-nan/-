### 0.6 已知实质差异（需修订，不是笔墨官司）

**本文 §3.3 的 7 态，缺失闭环稿要求的一等状态「待核验」。**

| 项 | 闭环稿 §6.1 | 本文 §3.3 | 差异性质 |
|---|---|---|---|
| 主链 | 草稿 → 就绪 → 执行中 → **待核验** → 完成 | DRAFT → READY → RUNNING → DONE | `DONE` 把「完成」与「待核验」压成一态 |
| 受阻 | 人 / 数据 / 依赖 / 资源 四因 | 仅 `BLOCKED_NEEDS_HUMAN` | 只表达"等人" |

**为什么这不是小事**：闭环稿要求外部动作结果未确认时保持「待核验」，不得计完成——施工单 T1 已强制 `businessStatus=PENDING_VERIFICATION`，原 `state=DONE` 一律标待核验。本文 7 态若继续压成一态，总账就会把"人工报告完成"当"已核验完成"。**这正是"假完成"的制度化入口。**

影响范围：`dist/src/system-state.js` 现有映射继承了这两处简化。**修法须在共同开发计划内排期，本文不擅自改代码。**

**已实测到一处直接后果（2026-10-26 11:40）**：`run-state.json` 的 `READY_FOR_LOGIN`（空闲待启动）被映射为 `BLOCKED_NEEDS_HUMAN`，在总账形成一条挂了 19.9 小时的假 Gate，稀释了两条真实待决（`FINAL_REVIEW` / `FACTS_CHECK`，各挂 21.7 小时）。且三条 Gate 全部无人响应。**假阳性比缺失更危险——它会训练人忽略所有告警。**

## 一、框架不是模块清单，是五个必须回答的问题

任何运营系统，无论 ERP、BI 还是自建，只要能回答这五问，就是完整的；缺一个就是残的。

| # | 问题 | 答不上来的后果 |
|---|---|---|
| 1 | **有什么东西？**（对象模型） | 每来一个需求就新写一套表，越写越乱 |
| 2 | **它现在什么样？**（状态真源） | 问"现在什么情况"只能靠猜 → 秘书编进度 |
| 3 | **谁能对它做什么？**（能力与副作用） | 改价、发布、删数据共用一套权限 |
| 4 | **什么时候该动手？**（驱动机制） | 全靠人想起来，运营周期空转 |
| 5 | **怎么知道做错了？**（验证与纠错） | 错了没人发现，直到钱少了 |

**当前系统在第 2 问上是明确不及格的**，这是第一优先级，不是数据问题。

## 二、五层架构：每层只能通过契约访问下一层

```
┌─ L5 控制层 ─────────────────────────────────────────────┐
│  对话入口（唯一总控）                                     │
│  只做三件事：理解意图 → 选能力/编排 → 在 Gate 停下问人     │
└──────────────────┬──────────────────────────────────────┘
                   │ 只能调「能力」，不能直接读文件/点页面
┌─ L4 决策层 ──────┴──────────────────────────────────────┐
│  策略库：分层 / 风险 / 节拍器 / 阈值器                    │
│  输入 facts → 输出 WorkUnit 建议（不是直接执行）          │
└──────────────────┬──────────────────────────────────────┘
                   │ 只能创建 WorkUnit，不能调能力
┌─ L3 编排层 ──────┴──────────────────────────────────────┐
│  WorkUnit 统一状态机 + Gate 决策门                        │
│  负责：阶段推进、断点续跑、待决挂起、事件留痕              │
└──────────────────┬──────────────────────────────────────┘
                   │ 只能按 Capability 声明调用
┌─ L2 能力层 ──────┴──────────────────────────────────────┐
│  Capability Registry：140 路由 → 声明式能力               │
│  每个能力带：入参 schema / 副作用等级 / 幂等键 / 验证方法  │
└──────────────────┬──────────────────────────────────────┘
                   │ 只写 facts，不写派生结论
┌─ L1 事实层 ──────┴──────────────────────────────────────┐
│  append-only facts，幂等，带 reason/coverage             │
│  指标永不久居：每次从 facts 重算                          │
└──────────────────┬──────────────────────────────────────┘
                   │ 只读
┌─ L0 外部世界 ────┴──────────────────────────────────────┐
│  店小秘 · 速卖通后台 · 1688 · 稳卖浏览器                  │
└─────────────────────────────────────────────────────────┘
```

**这条"只能"是框架的核心价值。** 它把"平行真相"从制度约束变成结构约束——想绕开都没有通道。现在系统里之所以能出现 6 套状态，就是因为没有这条线。

## 三、核心抽象一：WorkUnit（统一工作单元）

### 3.1 为什么必须有它

系统现在的**所有业务本质同构**，但实现成了 6 套：

| 载体 | 主键 | 状态字段 | 进度 | 明细 | 事件流 | 落盘 |
|---|---|---|---|---|---|---|
| `charm_listing_jobs` | id | status + current_stage | checkpoint | drafts / attempts | ✅ charm_events | SQLite |
| `batch-listing-state` | jobId | running(bool) | overallProgress | items | ❌ | JSON |
| `collect-batch-state` | jobId | running(bool) | overallProgress | rows | ❌ | JSON |
| `run-state` | 无（单例） | stage + running | imageCount | imageNames | ❌ | JSON |
| `data-collection-tasks` | taskId | ？ | ？ | ？ | ❌ | JSON |
| `daily-waiting-items` | ？ | ？ | — | items | ❌ | JSON |

语义完全同构（一个目标 + 一串步骤 + 若干待决点 + 一个产物），结构全异构。
**后果：只有 1/6 有事件流，只有 1/6 能断点续跑，1/6 能回答"到哪了"。**

### 3.2 统一结构

```json
{
  "unitId": "wu_20261025_xxxx",
  "kind": "LISTING | BATCH_UPLOAD | COLLECT | OPS_ACTION | REPLENISH | CLEARANCE | REVIEW",
  "goal": "人类可读的一句话目标",
  "state": "DRAFT | READY | RUNNING | BLOCKED_NEEDS_HUMAN | DONE | FAILED | CANCELLED",
  "stage": "当前阶段名",
  "stageIndex": 2, "stageTotal": 5,
  "gate": { "reason": "...", "needFrom": "human", "options": [...] },
  "payload": { "入参快照（不可变）" },
  "artifacts": [ { "type": "draft|image|receipt|file", "ref": "..." } ],
  "metrics": { "progress": 0.6, "itemsDone": 3, "itemsTotal": 5 },
  "idempotencyKey": "内容指纹",
  "createdBy": "human | agent | scheduler | threshold",
  "createdAt": "...", "updatedAt": "...", "finishedAt": null
}
```

### 3.3 七个状态覆盖全部现有语义

> ⚠ **本节部分从属（见 §0.4 / §0.6）**：闭环稿 §6.1 要求「待核验」为一等状态，且「受阻」含人/数据/依赖/资源四因。本文 7 态把「完成」与「待核验」压成一态、受阻只留"等人"，属已知差异，修订须排入共同开发计划。本节保留原文以便复核差异。

| 现有说法 | 统一状态 |
|---|---|
| QUEUED / 待开始 | `READY` |
| running=true / stage=作图 | `RUNNING` |
| REVIEW_REQUIRED / NEEDS_INPUT / pauseRequested | `BLOCKED_NEEDS_HUMAN` |
| PUBLISHED / progress=100 且无错 | `DONE` |
| error / publishFail | `FAILED` |
| 手动停止 | `CANCELLED` |
| 尚未提交 | `DRAFT` |

**关键设计：`BLOCKED_NEEDS_HUMAN` 是一等状态，不是异常。** 人工介入是设计的一部分，不是流程失败。这样"等谁拍板"才能变成可枚举清单。

### 3.4 事件流强制

任何 WorkUnit 的每次状态跃迁、每次能力调用、每次 Gate 决策，都必须追加一条事件。**没有事件的跃迁视为非法**（开发期直接报错，生产期记 WARN）。

现在 5/6 系统没有事件流，所以"卡在哪"永远查不出来。这是 L3 必须补的第一件事。

## 四、核心抽象二：Capability（能力声明）

### 4.1 不直接暴露 140 个路由

| 问题 | 裸调路由 | 能力声明 |
|---|---|---|
| 我知道有哪些操作吗 | 要读 140 个路由 | 一张注册表 |
| 这个操作危险吗 | 要读实现 | 副作用等级写在声明里 |
| 重复调用会怎样 | 要读实现 | 幂等键写在声明里 |
| 做完算成功吗 | 要靠猜 | 验证方法写在声明里 |
| 失败能退吗 | 大多不能 | 回滚方式写在声明里 |

**140 个端点就是 140 个隐患。** 但也不需要一次注册完——只注册 20 个高频能力，覆盖 95% 日常操作即可。

### 4.2 能力声明结构

```json
{
  "id": "listing.run",
  "label": "生成 Listing 内容",
  "endpoint": "POST /api/listing/run",
  "params": { "images": "string[]", "profile": "string", "facts": "object?" },
  "sideEffect": "P2",
  "idempotency": "contentHash(params)",
  "precheck": ["images 至少 1 张且可读"],
  "verify": "返回 draft 必须含 title + description + 至少 1 条属性",
  "rollback": "无副作用，可重复生成",
  "produces": { "unitKind": "LISTING", "artifacts": ["draft"] }
}
```

### 4.3 副作用分级 P0–P6（在代码里强制，不写在提示词里）

| 级 | 含义 | 授权 |
|---|---|---|
| P0 | 纯读 | 自由执行 |
| P1 | 写本地事实/草稿 | 自由执行 |
| P2 | 生成本地文件（图片/文档） | 自由执行 |
| P3 | 改平台草稿态数据 | **需人批** |
| P4 | 改价 / 改库存 | **需人批 + 金额上限** |
| P5 | 发布 / 上架（不可逆外部动作） | **必须人点** |
| P6 | 删除 / 清空 / 回滚 | **每次单独确认** |

**P5 必须人点** 不是保守，是因为系统目前是无人值守批量架构，一次误发污染的是整店。

## 五、核心抽象三：Gate（决策门）

### 5.1 现在的问题

系统里共有 4 处"需要人拍板"，实现方式各不相同：审核令牌、`pauseRequested`、`NEEDS_INPUT` 状态、前端弹窗确认。**判断逻辑散落在代码各处 if 里，没有一个地方能列出"现在一共在等谁"。**

### 5.2 统一 Gate

```json
{
  "gateId": "g_xxx", "unitId": "wu_xxx",
  "kind": "APPROVAL | INPUT_NEEDED | AMBIGUITY | RISK_ALERT",
  "question": "这一版标题和主图可以发布吗？",
  "options": [
    { "id": "approve", "label": "通过并发布", "sideEffect": "P5" },
    { "id": "revise",  "label": "要改（说明改哪里）" },
    { "id": "reject",  "label": "放弃这个商品" }
  ],
  "blockedSince": "ISO8601",
  "defaultIfIgnored": "stall"
}
```

**一条硬规矩：`defaultIfIgnored` 只能是 `stall`（原地等），绝不能是"超时自动通过"。** 无人值守不等于无人负责。

## 六、主线：双环共用一套总控

> ⚠ **本节已被取代（见 §0.4）**：业务闭环以 `docs/superpowers/specs/2026-10-26-ceo-os-operating-loop-design.md` §3 闭环表 + §4 节奏细则为准。本节保留为历史思路与接缝论证。

### 6.1 商品环（项目型，有始有终）

```
选品 → 建档 → 内容生成 → 审核 → 上架 → 在售运营 → 退出/归档
```
前四步基本已建成（②③ 合体后），后两步是当前最大的空白。

### 6.2 店铺环（周期型，日/周/月）

```
日扫（异常+待决） → 周复盘（分层+归因） → 月盘点（结构+资金）
                    ↓ 阈值触发
              生成 WorkUnit（补货 / 调价 / 清库 / 诊断）
```

日扫只做三件事、输出**上限 3 条**紧急工单。这是刻意设的上限——运营系统最常见的死法是告警太多导致全部被忽略。

### 6.3 两环的接缝就是 WorkUnit

商品环产出 WorkUnit（上品任务），店铺环产出 WorkUnit（运营动作）。**两者同构，所以能进同一个总账、用同一套 Gate、走同一条事件流。**

这就是为什么必须先统一 WorkUnit 再谈闭环——不统一，两环永远各说各话。

## 七、真实缺口：三个，全在框架层

| 缺口 | 现状 | 后果 |
|---|---|---|
| **无统一 WorkUnit** | 6 套并行状态机，5 套无事件流 | 答不出"现在什么情况"，无法断点续跑 |
| **无 Capability Registry** | 140 路由裸奔，权限散落在 if 里 | 无法判断"这个操作危不危险、重不重" |
| **无统一 Gate** | 4 处拍板逻辑各不相同，唯一带令牌的是空壳 | 无法列出"在等谁"，人工环形同虚设 |

**数据层不是缺口。** facts 管道、口径字典、商品分层已经跑通，它们是 L1 的插件，框架立起来后随时能换。

## 八、落地顺序：F1→F5，按依赖不按模块

> ⚠ **本节已被取代（见 §0.4）**：协同合同已明确「不按历史 W3/F2 或模型适配草案直接开工」。落地顺序以共同开发计划为准；本节保留为依赖关系的论证，不构成开工依据。

| 阶段 | 做什么 | 风险 | 为什么排这里 |
|---|---|---|---|
| **F1** | 统一 WorkUnit 视图 + 状态总账 `GET /api/system/state` | **零**（只读聚合，不删旧表） | 看不见就不能驱动；它是后面四步的地基 |
| **F2** | Capability Registry，先注册 20 个高频能力 | 低（不改变现有调用） | F1 告诉你"该动什么"，F2 才告诉你"怎么动" |
| **F3** | 统一 Gate + 事件流强制 | 中 | 有了 F1 的总账，Gate 才有地方挂 |
| **F4** | 决策层接入：分层/风险/触发器 → 自动生成 WorkUnit | 中（会开始自动创建任务） | 前置是 F1 的账 + F2 的手 |
| **F5** | 控制层接上：对话入口只调能力、只过 Gate | 低 | 最后接，因为前面的契约稳了它才稳 |

### F1 为什么必须先做，且只做只读

它带来三样立刻可用的东西，且**不动任何业务逻辑**：

1. 你问"现在怎么样"，第一次能拿到准确答案而不是猜
2. "卡在哪"变成可枚举清单 → 你才知道真正该修什么
3. 它会顺手暴露一批真实故障：挂着的 job、卡三天的 NEEDS_INPUT、state 与磁盘不一致

而且它做完之后，F2 的选型（注册哪 20 个能力）才有数据支撑——不然是拍脑袋。

## 九、验收：框架立起来的判断标准

> ⚠ **本节已被取代（见 §0.4）**：验收权威为闭环稿 §10 的 B0–B15（16 条，含独立交叉核对）。本节 6 条保留为技术层自检清单，不是验收通过依据。

不写"架构完成"，写可验证的条件：

| # | 条件 | 验证方法 |
|---|---|---|
| 1 | 能一次答清"现在在跑什么" | `GET /api/system/state` 返回全部活跃 WorkUnit，且与各 state 文件逐条比对一致 |
| 2 | 任一 WorkUnit 可追踪全程 | 给定 unitId 能拉出完整事件时间线，无断点 |
| 3 | 危险操作无法绕过 Gate | 直接调 P5 能力会被拒，且拒绝原因明确 |
| 4 | 断点可续 | 杀掉 server 重启后，RUNNING 的 WorkUnit 能恢复到正确阶段 |
| 5 | 数据断流不冒充健康 | facts 缺失时总账显式标 `DATA_STALE` 并给出原因，不回落旧值 |
| 6 | 有两个客户端的同一视图 | 对话入口与网页看到的是同一份状态（同源，不是各自拼） |

**第 6 条是"平行真相"的最终检验。**

---

## 十、三条不可妥协的红线

1. **指标永不入库为唯一真相。** 只落 facts，派生结论每次重算。口径一改，历史自动按新口径重出。
2. **宁可说"不知道"，不能说错。** 数据缺失 → `null + reason` → 显式 `DATA_STALE`。绝不用上一周期数值填充。
3. **P5/P6 永远人点。** 且超时不会自动通过，只会 stall。

### 载体 → 统一 7 态映射（实测校准）

| 载体 | 原始表示 | 映射规则 |
|---|---|---|
| `run-state.json` | `stage` + `running` | 完成/失败态优先 → pauseRequested → running → `stage` 含 LOGIN 判 BLOCKED |
| `batch-listing-state` | `running` + `remaining` | running → RUNNING；100% 且 success>0 → DONE；100% 且 success=0 → FAILED |
| `collect-batch-state` | 同上 | 同上 |
| `charm_listing_jobs` | `status` | 显式映射表 `CHARM_STATUS_MAP`，不模糊匹配 |
| `data-collection-tasks` | `status` | pending/running/analyzed/failed/cancelled |
| `daily-waiting-items` | `status` | resolved → DONE；其余 → BLOCKED（等外部方） |
| `queue-state` | `tasks[]` + `running` | **空队列不生成单元**（空壳不是待办） |

### 三个跨源统一校验（必须在主入口，不能交给各适配器）

1. **ZOMBIE_RUNNING（P1）**——标记 RUNNING 但状态超过 5 分钟未更新。实测抓到：一个 job 标 `PUBLISHING` 却已 67 天未动，是"假运行"。
2. **BLOCKED_WITHOUT_GATE（P2）**——状态为等待人工但没记录等待原因/对象。自动按 stage 兜底推断并报警，防止出现"说不出在等什么"的空 Gate。
3. **STALLED_BLOCKED（P2）**——阻塞超 24 小时。

> 这三个检查放主入口而非适配器：否则每新增一个载体就会漏检一类问题。这是框架层的教训。

### 活跃 / 归档分离

- DONE / CANCELLED 超过 **7 天** → 归档
- FAILED 超过 **30 天** → 归档（**失败需要人决策，不能因时间久了就自动消失**）
- 归档只给索引，不进 `units` / `gates` / `anomalies`

实测效果：13 个单元 → **5 个活跃 + 7 个归档**，4 个月前的测试数据不再淹没真问题。

### 验收结果

`node scripts/verify-system-state.mjs` → **19/19 PASS**

其中关键几条：
- `byState` 之和 == `unitCount`
- `run-state` 的 stage 与文件逐字一致
- SQLite 3 个 job 全部收录且 stage 与库一致
- 每个 Gate 都有 question 且 `defaultIfIgnored=stall`
- 7 个源全部可读
- **progress 量纲统一为 0–100 或 null**（防回归，见下方"量纲事故"）

**只读硬验证**：连续 20 次请求后，7 个源文件的 `mtime+size` 聚合指纹完全不变。
（SQLite 的 `-shm`/`-wal` 会因连接而变动，属 SQLite 正常行为，非业务写入。）

| 问题 | 后果 |

| `charm_job_f1a3...` 的 NEEDS_INPUT 卡了 **1613 小时**（67 天） | 一个商品等输入等了两个月，此前无人发现 |

### 已知限制

1. **面板只读，不能动手**：这是 F1 的刻意边界。页面上的按钮只有「立即刷新」，没有任何写入口。想推进业务必须等 F2 能力层——**在视图里开侧门就等于又造了一条平行通道**。
2. **`current_stage` 语义靠约定**：`run-state` 的 stage 是自由字符串，本模块只用完成/失败/登录几类关键词判定，未穷举。
3. **不做数据新鲜度裁决**：总账只报 `ageMs`，够不够支撑决策是 L4 的事。面板会点名陈旧源（当前 2 个：经营数据采集任务 127 天、每日待办 124 天），但不会自作主张判死。
4. **`progress` 大量为 null**：因为多数载体本身不记进度，不是我们没读。
5. **同一单元会在两块出现**：「等你拍板」与「在跑什么」是同一份数据的两个视角（待决策 vs 全景），不是重复计数。

## 十一·B、F1 前端面板（2026-10-25 已交付）

### 位置与形态

挂在**今日驾驶舱（`daily-cockpit`）首屏第一块**——默认视图，打开就能看见，不需要多点一层。

面板四段：

| 段 | 内容 | 设计意图 |
|---|---|---|
| 摘要四格 | 活跃单元 / 等你拍板 / 需要处理 / 已归档 | 十秒内知道「今天有没有事」 |
| 等你拍板 | 每条 Gate 的问题、原因、已等多久 | 行尾明确写「超时不会自动通过，只会一直停在这里」 |
| 需要处理 | 异常按 P0→P2 排序，带证据时间 | P1/P2 一眼分辨 |
| 在跑什么 | 全部活跃单元：状态、阶段、更新于 | 「假运行」在这里现形 |
| 脚注 | 源可读数、**逐个点名的陈旧源**、只读声明、生成时刻 | 诚实机制 |

### 三条前端设计约束（都是踩过才定的）

1. **不跟随 1s 主循环，用 15s 独立轮询。** 总账是聚合视图不是实时指标；跟着 `refresh()` 跑只会每秒重读 7 个状态源。
2. **指纹差异更新，响应未变绝不重写 DOM。** 页面本身每秒全量重绘，此处若盲目重建，用户阅读时会不停闪、展开状态也会丢。验收脚本专门测这条（3 秒后同一 DOM 节点仍存活）。
3. **不可见时不请求。** 面板不在激活视图或标签页隐藏时跳过，`visibilitychange` 回来立刻补一次。

### 量纲事故（值得单独记一笔）

第一版面板把 `overallProgress=100` 渲染成了 **「进度 1%」**，而同一行的批次说明写着「进度 100%」——**两个数自相矛盾，两边代码各自都"自洽"**。

根因：`system-state.js` 把 0–100 的 `overallProgress` 又除以 100（当成 0–1 比值），而验收脚本也按 0–1 写的断言 `u.progress * 100 === raw.overallProgress`——**验收和实现犯了同一个错，所以 18/18 全绿**。

修法不是改除不除，而是**定死契约**：`progress` 全响应统一 0–100 或 null，验收脚本加一条量纲守卫。前端不需要任何改动，因为 `%` 本来就该配 0–100。

> 教训：验收脚本若由实现者按同一假设写成，它只能证明"代码符合我的假设"，不能证明"假设是对的"。量纲、单位、时区这类跨层约定，必须有一个不依赖实现者的检查点（这里是肉眼截图 + 交叉矛盾发现）。
