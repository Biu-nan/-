# 上品写词链路的优化方案（v1）

- 日期：2026-11-05
- 起点：词库已建、注入已接（`docs/KEYWORD_LIBRARY_2026-11-05.md`），但**注入只是建议，模型可以不理**
- 本轮新增两个量化工具：`scripts/lint-listing-keywords.mjs`（埋词校验）、`scripts/build-category-map.mjs`（类目映射候选）

## 0. 结论先行：四层优化，只有第一层是"现在就缺"的

| 层 | 问题 | 优化手段 | 收益 | 成本 |
|---|---|---|---|---|
| **L1 强制层** | 注入是建议，模型可以不用 | **产出后校验 gate**（已实现） | 让"有没有埋词"从不可知变成可判定 | 0 |
| **L2 粒度层** | 12426 一级库 51 词，69/74 撞 `key chain` | 下抓二级/叶子关键词榜 | 主词从"类目词"变"子类词" | 30/子类 |
| **L3 覆盖层** | 47/132 无类目规则 | 受控词表 + 人工确认（**不是自动匹配**） | 覆盖率 56% → 90%+ | 人力 |
| **L4 验证层** | 不知道换词有没有用 | 上线 7 天后用自家数据做后验 | 回答"值不值" | 0 |

## L1 强制层：埋词校验（已实现并跑出数）

`scripts/lint-listing-keywords.mjs` 三条断言：

| 断言 | 含义 | 历史 74 份 SEO 产物实测 |
|---|---|---|
| **G1** 主词是否进了 SEO 词库 | 该用没用 = 白注入 | **74/74 不含库主词**（库是新东西，属基线，不算历史过错） |
| **G2** 标题是否包含主词 | 标题不含主词 = 埋词没做 | **12/74 FAIL（16%）** |
| **G3** 是否出现红海词/品牌词 | 烧钱 + 侵权 | 0/74（历史 prompt 里本来就有禁令，这条守住了） |

**G2 那 12 个是关键**：它们是"词对了但标题里没用"的实例——这正是注入层解决不了、只能靠校验发现的问题。

建议接法（未实施，等你定）：
```
listing 生成完成 → lint → PASS 才允许进入 REVIEW 队列
                        → FAIL 标记 REVIEW_REQUIRED，写 run-state.lintKeyword
不自动改稿、不自动重跑（守住 P5 红线：发布必须人点）
```

## L2 粒度层：为什么会撞 `key chain`

回溯 74 个可注入产品，库选词分布：

```
key chain          69
storage             2
organizer           2
photocard holder    1
```

原因不是算法错，是**词库太粗**：12426（箱包）在 IXSPY 里有 20+ 二级子类，但关键词榜只到一级，51 个词里 A 层只有 8 个，撑不住"钥匙扣/挂件/卡包/包带/链条"的区分。

优化：
1. 对 12426 下**有真实销量的二级类目**逐个抓 `keyword_rank`（30 积分/个），把词库从"一级"下沉到"二级"；
2. 优先抓这几个（来自 P0 榜单实测的高频路径）：`15008 箱包配件`、`25900→25906 便携式折叠包`、`6560 男士包袋`、`12431 特殊用途箱包`；
3. 抓不到（覆盖 0）的类目继续用**竞品标题词库**兜底（已有 210 个单品挖词，0 积分可扩）。

预算：4 个子类 × 30 = **120 积分/月**（月更即可，关键词榜本身周更但词库不必周更）。

## L3 覆盖层：类目映射**不要**做全自动（这条是负面结论）

我试了用 13,566 节点分类树做名称模糊匹配，结果不可用：

| 产品 | 自动匹配结果 | 荒谬点 |
|---|---|---|
| 3D打印解压玩具（标题含 "press"） | 木工压机（工业和商业） | 动词 press ≠ 压机 |
| 3D耗材收纳袋（"Non Woven Fabric"） | 面料（DIY 缝纫） | 材质词 ≠ 类目 |
| 南瓜万圣手提袋（"lantern"） | 灯笼（室外照明） | 手提袋 ≠ 灯笼 |
| 折叠式耗材收纳箱（"accessories"） | 健身器材配件 | 泛化词撞车 |

连 `high` 置信度都是错的。**结论：名称匹配只能用来"排序候选"，不能用来定案。**

正确做法（建议）：
1. 用 `category_lookup`（**0 积分**）按中文名精确查一遍候选；
2. 474 个在售品**一次性人工确认**（这是有限工作量，一次做完长期复用）；
3. 结果固化成 `data/keywords/category-map.json`（productId → categoryId），比现在的手写规则稳；
4. 之后只对新增品做增量。

`scripts/build-category-map.mjs` 保留作为"候选生成器"，输出 `data/keywords/category-map.json` 供人工过一遍，**不自动写 rules**。

## L4 验证层：怎么知道换词有没有用

现在缺的是闭环。可用的两个信号（都是自家数据，0 积分）：

| 信号 | 来源 | 用法 |
|---|---|---|
| 新品 7 日曝光 / 访客 / 支付件 | 商品分析 `dps.query`（L4 已通） | 上线 7 天后回填，按"词来源"分组比较 |
| 关键词搜索排名 | 需另找数据源 | 暂无，先用曝光代理 |

落地方式：给每个 listing 打标 `keywordLibrary: {action, primary}`（已写入 run-state），30 天后就能算：
- `override` 组 vs `supplement` 组 vs `无注入` 组的新品 7 日曝光中位数
- 这是唯一能回答"词库到底有没有用"的方法，现在做不了，因为样本还没跑出来。

## L3 修正（2026-11-05 14:15，重要）：映射不需要人工勾选，因为两边是同一套词表

前面 §L3 的负面结论只对"模糊匹配"成立，对"全等匹配"不成立。实测：

| 输入（店小秘 `categoryNameZh`） | IXSPY 树全等命中 | 结果 |
|---|---|---|
| `收纳盒和收纳箱（有关婴儿食品储存的请发布到婴儿食品存储盒下）` | ✅ | **11210** 家居用品>家用储存收藏用具>收纳盒和收纳箱（…） |
| `Storage Boxes & Bins`（同一节点的英文名） | ✅ | 同上 11210 |
| `Luggage & Bags` | ✅ | **12426** 箱包（L1） |
| `钥匙扣`（LLM 自造词） | ❌ | 树里没有这个节点 |

**关键事实：店小秘的 `categoryNameZh` 与 IXSPY 的 `name_localized` 是同一套平台类目词表**（连那句长括号提示都一字不差）。所以：

- 映射方式 = **全等 join**，0 积分、0 歧义、可复现；
- 索引规模：中文名 13,091 条 / 英文名 13,043 条（13,566 节点）；
- **不需要人工逐条勾选**；
- 之前 47 个 `NO_CATEGORY_RULE` 的根因不是"词表不同"，而是 **`product-facts.category` 是 LLM 写的自由文本，不是平台类目名**（如"创意钥匙扣 / 包挂 / 键盘造型挂件"），自然命中不了。

### 因此正确的第 2 步是

1. 从店小秘只读抓 474 个商品的 `categoryNameZh`（CDP 9223，**0 积分**）；
2. 离线全等 join 出 `category_id` → 写 `data/keywords/category-map.json`；
3. **只有未命中的才需要人工判断**（预计个位数，因为平台类目极少超出 IXSPY 树；若超出说明 IXSPY 树快照旧了，需等新树）。

### 副产物：这同时修掉了另一个老问题

`product-facts.category` 一直由模型自由生成（38 种取值、其中 92 份为空），既不能 join 也不能统计。若改为**从店小秘 `categoryNameZh` 继承**，则：
- 类目变成平台权威值，不再由模型编；
- 关键词映射、类目分层、榜单对比全部可用同一套 ID。
